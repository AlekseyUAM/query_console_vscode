# Дорожная карта проекта

Общий план конструктора запросов 1С для VS Code: куда идём, на какие подсистемы
разбит проект и в каком состоянии каждая фаза. Документ живой — обновляется по мере
закрытия итераций.

См. также: [README](../README.md) · [исходные требования](../README.md#исходные-требования-и-контекст).

## Видение

Повторить классический «Конструктор запроса» из Конфигуратора/EDT: вкладки Таблицы и
поля, Связи, Группировка, Условия, Дополнительно, Индекс, Объединения/Псевдонимы,
Порядок, Итоги, Построитель, Пакет запросов — плюс двунаправленность: генерация текста
запроса из визуальной модели **и** обратный разбор существующего текста обратно в
конструктор.

Это слишком много для одной итерации, поэтому проект декомпозирован на подсистемы и
строится вертикальными срезами: каждая итерация проходит сквозь нужные слои и
закрывается отдельным циклом **спек → план → реализация**.

## Подсистемы

| # | Подсистема | Каталог | Роль |
|---|---|---|---|
| 1 | Слой метаданных | `src/core/metadata` | Парсинг выгрузки `cf` в модель «таблицы → поля → типы → связи» |
| 2 | Слой запроса (SDBL) | `src/core/query` | Генерация текста запроса из модели (в будущем — обратный разбор) |
| 3 | UI конструктора | `src/webview` | Webview с панелями и вкладками |
| 4 | Интеграция VS Code | `src/extension` | Команды, открытие панели, вставка результата в код |

Логика — в `core` (pure-TS, тестируется в Node), webview — «тонкий» UI. Контракт между
слоями сосредоточен в `src/shared/messages.ts`.

## Статус по фазам

Легенда: ✅ готово · 🚧 в работе · ⬜ запланировано

Полное описание каждой фазы (со всеми подфазами, ссылками на спеки и планы) — в
отдельных файлах `PHASE_<N>.md`.

### ✅ [Фаза 0. MVP — вертикальный срез](PHASE_0.md)

Сквозной срез через все 4 слоя: команда `1С: Конструктор запроса` открывает webview,
вкладка «Таблицы и поля» генерирует `ВЫБРАТЬ … ИЗ …` и вставляет текст в редактор.

### ✅ [Фаза 1. Парсер метаданных → YAML](PHASE_1.md)

Парсер выгрузки 1С в каталог YAML-файлов как переиспользуемый артефакт и контракт между
парсером и потребителями (справочники, документы, константы, перечисления).

### ✅ [Фаза 2. Конструктор читает YAML](PHASE_2.md)

Слой метаданных конструктора переведён на чтение YAML-артефакта парсера (или кэша из
него) вместо прямого пути `cfParser.ts`.

### ✅ [Фаза 3. Доработка UI конструктора](PHASE_3.md)

Drag&drop между панелями, табличные части и раскрытие ссылочных реквизитов в дереве,
вставка BSL-строки в позицию курсора, контекстное меню `.bsl`.

### ✅ [Фаза 4. Расширение типов метаданных](PHASE_4.md)

Новые виды таблиц поверх общего конвейера парсера: 17 типов метаданных, виртуальные
таблицы регистров (сведений, накопления, бухгалтерии) и сквозной golden-сьют текстов
запросов.

### ✅ [Фаза 5. Вкладки конструктора](PHASE_5.md)

По одной фиче на вкладку поверх стабильного ядра: Группировка, Условия, Дополнительно,
Объединения/Псевдонимы, Связи, Порядок, Итоги, Пакет запросов, Построитель, Индекс.

### ✅ [Фаза 6. Обратный разбор текста запроса](PHASE_6.md)

Двунаправленность: из текста запроса SDBL восстанавливается визуальная модель
(инверсия генератора) рукописным pure-TS парсером. Оба корпуса рендерятся побайтно как
конструктор 1С (golden-оракул `validate_query`): базовая конфигурация 1976/1976 и вторая
(большая) конфигурация 17933/17933 — 0 mismatch, 0 parse-exception.

### ✅ [Фаза 7. Открытие конструктором существующего текста запроса](PHASE_7.md)

UX поверх парсера Фазы 6: единственная команда `1С: Конструктор запроса` по ПКМ в
тексте запроса разбирает литерал под курсором и открывает конструктор уже заполненным
(Таблицы, Поля, Условия), как если бы запрос собрали руками. Если текст запроса не
найден — модальный вопрос «Не найден текст запроса. Создать новый запрос?», и только по
согласию открывается пустой конструктор. Лишняя команда `(из позиции)` удаляется.
Подфазы: 7.1 единая команда, 7.2 консолидированный кэш метаданных (~13.5с → ~0.3с),
7.3 разведка **реального** конструктора 1С через Playwright (tooling-драйвер живого
веб-клиента + визуальный референс) — вход для будущей сверки на корпусе (7.4).

### ✅ [Фаза 8. Сохранение комментариев и доработки](PHASE_8.md)

Возможности поверх двунаправленного ядра, не ломающие канонический вывод оракула.
Подфаза 8.1 — **сохранение комментариев** запроса (`//…`): при открытии конструктором
комментарии 4 видов привязываются к смысловым якорям модели (имя ВТ / номер пакета,
синоним поля, `ВЫБРАТЬ`, `ИЗ`) и переживают цикл *открыть → править → сохранить*.
Галочка «Сохранять комментарии» в шапке (рядом с «Обновить кэш»), включена по умолчанию.
Сбор комментариев — **opt-in** (`parseBatch(..., { preserveComments:true })`), поэтому
золотой оракул и регрессия корпуса 1976 запросов остаются байт-в-байт. Подфаза 8.2 —
исследование инструмента семантической валидации; 8.3 — доработки конструктора (UX/
корректность/производительность); 8.4 — **локальная семантическая валидация открытия**:
запрос на несуществующую таблицу больше не открывается (проверка по кэшу метаданных, без
вызова MCP в рантайме), с принципом fail-open против ложных срабатываний.

## Ключевые архитектурные решения

- **Отдельное расширение, свой парсер метаданных** — независимость от
  `vscode-1c-platform-tools`, чистые границы.
- **«Тонкий webview»** — вся логика в `core` (pure-TS), webview не знает про файлы,
  `core` не знает про React/vscode. Обязателен TDD.
- **Только генерация в MVP** — обратный разбор добавлен в Фазе 6 рукописным pure-TS
  парсером (не tree-sitter в рантайме), симметрично генератору.
- **YAML на диске как контракт** парсера — человекочитаемый артефакт верификации,
  переиспользуемый другими проектами.
- Полный список и обоснования — в [MVP-спеке](superpowers/specs/2026-06-01-1c-query-constructor-mvp-design.md) (раздел 2).

## Принцип итераций

Каждая фаза — самостоятельный цикл: **спек** (`docs/superpowers/specs/`) → **план**
(`docs/superpowers/plans/`) → реализация по TDD. Ядро (`QueryModel`, контракт
сообщений, модель метаданных) остаётся стабильным; новые возможности добавляются
секциями/модулями, не ломая существующее.
