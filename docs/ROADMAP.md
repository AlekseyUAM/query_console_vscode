# Дорожная карта проекта

Общий план конструктора запросов 1С для VS Code: куда идём, на какие подсистемы
разбит проект и в каком состоянии каждая фаза. Документ живой — обновляется по мере
закрытия итераций.

См. также: [README](../README.md) · исходные требования — [`DESCRIPTION.md`](../DESCRIPTION.md).

## Видение

Повторить классический «Конструктор запроса» из Конфигуратора/EDT: вкладки Таблицы и
поля, Связи, Группировка, Условия, Дополнительно, Объединения/Псевдонимы, Порядок,
Итоги, Пакет запросов — плюс двунаправленность: генерация текста запроса из визуальной
модели **и** обратный разбор существующего текста обратно в конструктор.

Это слишком много для одной итерации, поэтому проект декомпозирован на подсистемы и
строится вертикальными срезами: каждая итерация проходит сквозь нужные слои и
закрывается отдельным циклом **спек → план → реализация**.

## Подсистемы

| # | Подсистема | Каталог | Роль |
|---|---|---|---|
| 1 | Слой метаданных | `src/core/metadata` | Парсинг выгрузки `cf` в модель «таблицы → поля → типы → связи» |
| 2 | Слой запроса (SDBL) | `src/core/query` | Генерация текста запроса из модели (в будущем — обратный разбор) |
| 3 | UI конструктора | `src/webview` | Webview с панелями и вкладками |
| 4 | Интеграция VS Code | `src/extension` | Команды, открытие панели, вставка результата в код |

Логика — в `core` (pure-TS, тестируется в Node), webview — «тонкий» UI. Контракт между
слоями сосредоточен в `src/shared/messages.ts`.

### ⬜ Фаза 4. Расширение типов метаданных

Новые виды таблиц поверх общего конвейера парсера: регистры (сведений, накопления,
бухгалтерии), планы видов характеристик и прочее. Каждый новый тип — тонкий модуль +
строка в диспетчере + строка в дереве UI.

#### 4.1. Парсер 17 типов метаданных

Все запрашиваемые типы объектов в парсере и загрузчике YAML (планы обмена, видов
характеристик, счетов, видов расчёта; бизнес-процессы и задачи; все четыре вида
регистров; последовательности, журналы документов, критерии отбора). Роль поля
регистра хранится в `category: 'dimension' | 'resource'`. Сами реальные таблицы; без
виртуальных таблиц (см. 4.2).

- Спек: [`specs/2026-06-03-phase4-metadata-types-design.md`](superpowers/specs/2026-06-03-phase4-metadata-types-design.md)
- План: [`plans/2026-06-03-phase4-metadata-types.md`](superpowers/plans/2026-06-03-phase4-metadata-types.md)

#### 4.2. Виртуальные таблицы регистров сведений + конструктор произвольных выражений

> Эта задача — то, что в дизайне 4.1 явно отложено в раздел «Что не входит в фазу 4».
> Спек/план ещё не написаны; ниже — требования к итерации.

Берём за основу скриншоты `tmp/meta/РегистрСведений` (поведение классического
конструктора запроса 1С). Объём:

- **Виртуальные таблицы в дереве метаданных.** У периодического регистра сведений
  (`InformationRegisterPeriodicity != Nonperiodical`) есть две виртуальные таблицы —
  `СрезПервых` и `СрезПоследних`. Они показываются в дереве «База данных» отдельными
  строками рядом с самим регистром (`РегистрСведений.<Имя>.СрезПоследних`), наравне с
  реальной таблицей регистра. Поля среза совпадают с полями регистра (`Период`,
  измерения, ресурсы, плюс `ПериодОкончание` у среза).
- **Кнопка «Параметры виртуальной таблицы».** В панели «Таблицы» — кнопка, активная
  для выделенной строки-виртуальной таблицы. Открывает модальное окно с параметрами.
  Для срезов это два параметра: **Период** (поле с выпадающим списком, принимает
  значение вида `&Период`) и **Условие** (текстовое поле с кнопкой выбора «…»).
- **Окно «Произвольное выражение».** Открывается по кнопке «…» поля Условие и по
  кнопке добавления поля в панели «Поля». Состоит из трёх частей:
  - *Поле* — дерево доступных полей источника (поля выбранной таблицы + узел «Все
    поля» с раскрытием ссылочных полей); элементы перетаскиваются/добавляются в
    результат.
  - *Функции языка запросов* — дерево заготовок: **Функции** (работы со строками, с
    датами, с числами, агрегатные, прочие), **Операторы** (арифметические, логические,
    прочие), **Прочее** (`ДАТАВРЕМЯ`, `ЗНАЧЕНИЕ`, `ТИП`, `СГРУППИРОВАНОПО`). Выбор
    функции вставляет в результат её шаблон с плейсхолдерами, напр.
    `ДОБАВИТЬКДАТЕ(<Дата>, <Тип>, <Количество>)`. Полный перечень функций — в
    [`tmp/1c-query-language.md`](../tmp/1c-query-language.md).
  - *Результат* — текстовое поле; по «ОК» текст возвращается в поле Условие (или
    добавляется новым полем в панель «Поля»).
- **Добавление произвольного поля.** Кнопка «+» в панели «Поля» открывает то же окно
  «Произвольное выражение»; по «ОК» выражение добавляется отдельным полем выборки.
- **Генератор SDBL.** Источник-виртуальная таблица рендерится как
  `РегистрСведений.<Имя>.СрезПоследних(<Период>, <Условие>) КАК <Псевдоним>`; при
  пустых параметрах — `СрезПоследних()`; поля выборки префиксуются псевдонимом
  виртуальной таблицы. Эталоны текста запроса — на скриншотах
  `tmp/meta/РегистрСведений`.

Затрагивает все слои: модель метаданных (флаг периодичности → виртуальные таблицы),
`QueryModel` и контракт сообщений (параметры виртуальной таблицы, произвольные
выражения), генератор SDBL, webview (дерево, два новых модальных окна, drag&drop в
конструкторе выражений). Остальные виртуальные таблицы регистров (Остатки, Обороты,
ОстаткиИОбороты, движения с субконто) — за рамками этой итерации.

#### 4.3. Виртуальные таблицы регистров накопления

Прямое продолжение 4.2 на регистры накопления — то, что 4.2 явно отложил. Переиспользует
ту же машинерию (виртуальные таблицы в дереве, окно «Параметры виртуальной таблицы», окно
«Произвольное выражение», диспетчеризация генератора). Объём:

- **Состав виртуальных таблиц по виду регистра.** Вид регистра (`RegisterType`:
  Остатки/Обороты) сохраняется парсером в `properties`. У любого регистра накопления есть
  ВТ `Обороты`; у регистра вида Остатки дополнительно — `Остатки` и `ОстаткиИОбороты`.
  Виртуальные таблицы показываются в дереве «База данных» отдельными строками рядом с
  регистром (`РегистрНакопления.<Имя>.Обороты`), как срезы регистров сведений.
- **Развёртка ресурсов.** Каждый ресурс `<R>` разворачивается в колонки ВТ: `Остатки` →
  `<R>Остаток`; `Обороты` → `<R>Оборот` (+ `<R>Приход`, `<R>Расход` у регистра вида
  Остатки); `ОстаткиИОбороты` → `<R>НачальныйОстаток`, `<R>КонечныйОстаток`, `<R>Оборот`,
  `<R>Приход`, `<R>Расход`. Измерения копируются как есть.
- **Параметры виртуальных таблиц.** Окно «Параметры виртуальной таблицы» параметрично по
  виду ВТ: `Остатки` — `Период` + `Условие`; `Обороты` — `НачалоПериода`, `КонецПериода`,
  `Периодичность` (выпадающий список), `Условие`; `ОстаткиИОбороты` — дополнительно
  `МетодДополнения` (выпадающий список Движения/ДвиженияИГраницыПериода).
- **Зависимость полей от периодичности.** Для `Обороты`/`ОстаткиИОбороты` набор полей
  зависит от выбранной `Периодичности` (Период/Запись/Регистратор/Секунда…Полугодие/Авто):
  чистый core-хелпер `accumPeriodFields` добавляет к измерениям/ресурсам соответствующие
  поля периода (`Период`, `Регистратор`, `НомерСтроки`, либо семейство `ПериодСекунда…
  ПериодГод` для Авто).
- **Генератор SDBL.** Источник-ВТ рендерится с позиционными параметрами по виду ВТ:
  `Остатки(<Период>, <Условие>)`, `Обороты(<Начало>, <Конец>, <Периодичность>, <Условие>)`,
  `ОстаткиИОбороты(<Начало>, <Конец>, <Периодичность>, <МетодДополнения>, <Условие>)`;
  `Периодичность`/`МетодДополнения` — голые слова SDBL. Эталоны — в спеке.

Спек: [`specs/2026-06-03-phase4-accum-virtual-tables-design.md`](superpowers/specs/2026-06-03-phase4-accum-virtual-tables-design.md)
План: [`plans/2026-06-03-phase4-accum-virtual-tables.md`](superpowers/plans/2026-06-03-phase4-accum-virtual-tables.md)

За рамками: регистр бухгалтерии (субконто), виртуальные таблицы регистра расчёта,
валидация выражений и обратный разбор (фаза 6).

#### 4.4. Виртуальные таблицы регистров бухгалтерии

Продолжение 4.3 на регистры бухгалтерии: `Остатки`, `Обороты`, `ОстаткиИОбороты`,
`ДвиженияССубконто` + `ОборотыДтКт` для корреспондентских регистров. Развёртка
счетов/субконто/ресурсов по виду ВТ, фиксированная арность источника, псевдоним ВТ
приведён к 1С-точному (имя объекта). За рамками: разворот небалансовых измерений в Дт/Кт,
параметры-субконто в окне.

- Спек: [`specs/2026-06-07-phase4-accounting-virtual-tables-design.md`](superpowers/specs/2026-06-07-phase4-accounting-virtual-tables-design.md)
- План: [`plans/2026-06-07-phase4-accounting-virtual-tables.md`](superpowers/plans/2026-06-07-phase4-accounting-virtual-tables.md)

### ⬜ Фаза 5. Вкладки конструктора

Поверх стабильного ядра `QueryModel` и контракта сообщений — по одной итерации на
группу вкладок: Связи (визуальные соединения), Группировка и Итоги, Условия (отбор),
Порядок, Объединения/Псевдонимы, Пакет запросов и временные таблицы. Генератор SDBL
добавляет соответствующие секции в фиксированном порядке языка запросов.

### ⬜ Фаза 6. Обратный разбор текста запроса

Разбор существующего текста SDBL обратно в визуальную модель через `tree-sitter-bsl`
(WASM). В MVP tree-sitter используется только как тест-оракул валидности; здесь —
полноценная интеграция для двунаправленности.

## Ключевые архитектурные решения

- **Отдельное расширение, свой парсер метаданных** — независимость от
  `vscode-1c-platform-tools`, чистые границы.
- **«Тонкий webview»** — вся логика в `core` (pure-TS), webview не знает про файлы,
  `core` не знает про React/vscode. Обязателен TDD.
- **Только генерация в MVP** — обратный разбор (tree-sitter в рантайме) отложен до Фазы 6.
- **YAML на диске как контракт** парсера — человекочитаемый артефакт верификации,
  переиспользуемый другими проектами.
- Полный список и обоснования — в [MVP-спеке](superpowers/specs/2026-06-01-1c-query-constructor-mvp-design.md) (раздел 2).

## Принцип итераций

Каждая фаза — самостоятельный цикл: **спек** (`docs/superpowers/specs/`) → **план**
(`docs/superpowers/plans/`) → реализация по TDD. Ядро (`QueryModel`, контракт
сообщений, модель метаданных) остаётся стабильным; новые возможности добавляются
секциями/модулями, не ломая существующее.
