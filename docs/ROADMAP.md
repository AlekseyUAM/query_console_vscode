# Дорожная карта проекта

Общий план конструктора запросов 1С для VS Code: куда идём, на какие подсистемы
разбит проект и в каком состоянии каждая фаза. Документ живой — обновляется по мере
закрытия итераций.

См. также: [README](../README.md) · исходные требования — [`DESCRIPTION.md`](../DESCRIPTION.md).

## Видение

Повторить классический «Конструктор запроса» из Конфигуратора/EDT: вкладки Таблицы и
поля, Связи, Группировка, Условия, Дополнительно, Индекс, Объединения/Псевдонимы,
Порядок, Итоги, Построитель, Пакет запросов — плюс двунаправленность: генерация текста
запроса из визуальной модели **и** обратный разбор существующего текста обратно в
конструктор.

Это слишком много для одной итерации, поэтому проект декомпозирован на подсистемы и
строится вертикальными срезами: каждая итерация проходит сквозь нужные слои и
закрывается отдельным циклом **спек → план → реализация**.

## Подсистемы

| # | Подсистема | Каталог | Роль |
|---|---|---|---|
| 1 | Слой метаданных | `src/core/metadata` | Парсинг выгрузки `cf` в модель «таблицы → поля → типы → связи» |
| 2 | Слой запроса (SDBL) | `src/core/query` | Генерация текста запроса из модели (в будущем — обратный разбор) |
| 3 | UI конструктора | `src/webview` | Webview с панелями и вкладками |
| 4 | Интеграция VS Code | `src/extension` | Команды, открытие панели, вставка результата в код |

Логика — в `core` (pure-TS, тестируется в Node), webview — «тонкий» UI. Контракт между
слоями сосредоточен в `src/shared/messages.ts`.

### ✅ Фаза 4. Расширение типов метаданных

Новые виды таблиц поверх общего конвейера парсера: регистры (сведений, накопления,
бухгалтерии), планы видов характеристик и прочее. Каждый новый тип — тонкий модуль +
строка в диспетчере + строка в дереве UI.

#### 4.1. Парсер 17 типов метаданных

Все запрашиваемые типы объектов в парсере и загрузчике YAML (планы обмена, видов
характеристик, счетов, видов расчёта; бизнес-процессы и задачи; все четыре вида
регистров; последовательности, журналы документов, критерии отбора). Роль поля
регистра хранится в `category: 'dimension' | 'resource'`. Сами реальные таблицы; без
виртуальных таблиц (см. 4.2).

- Спек: [`specs/2026-06-03-phase4-metadata-types-design.md`](superpowers/specs/2026-06-03-phase4-metadata-types-design.md)
- План: [`plans/2026-06-03-phase4-metadata-types.md`](superpowers/plans/2026-06-03-phase4-metadata-types.md)

#### 4.2. Виртуальные таблицы регистров сведений + конструктор произвольных выражений

> Эта задача — то, что в дизайне 4.1 явно отложено в раздел «Что не входит в фазу 4».
> Спек/план ещё не написаны; ниже — требования к итерации.

Берём за основу скриншоты `tmp/meta/РегистрСведений` (поведение классического
конструктора запроса 1С). Объём:

- **Виртуальные таблицы в дереве метаданных.** У периодического регистра сведений
  (`InformationRegisterPeriodicity != Nonperiodical`) есть две виртуальные таблицы —
  `СрезПервых` и `СрезПоследних`. Они показываются в дереве «База данных» отдельными
  строками рядом с самим регистром (`РегистрСведений.<Имя>.СрезПоследних`), наравне с
  реальной таблицей регистра. Поля среза совпадают с полями регистра (`Период`,
  измерения, ресурсы, плюс `ПериодОкончание` у среза).
- **Кнопка «Параметры виртуальной таблицы».** В панели «Таблицы» — кнопка, активная
  для выделенной строки-виртуальной таблицы. Открывает модальное окно с параметрами.
  Для срезов это два параметра: **Период** (поле с выпадающим списком, принимает
  значение вида `&Период`) и **Условие** (текстовое поле с кнопкой выбора «…»).
- **Окно «Произвольное выражение».** Открывается по кнопке «…» поля Условие и по
  кнопке добавления поля в панели «Поля». Состоит из трёх частей:
  - *Поле* — дерево доступных полей источника (поля выбранной таблицы + узел «Все
    поля» с раскрытием ссылочных полей); элементы перетаскиваются/добавляются в
    результат.
  - *Функции языка запросов* — дерево заготовок: **Функции** (работы со строками, с
    датами, с числами, агрегатные, прочие), **Операторы** (арифметические, логические,
    прочие), **Прочее** (`ДАТАВРЕМЯ`, `ЗНАЧЕНИЕ`, `ТИП`, `СГРУППИРОВАНОПО`). Выбор
    функции вставляет в результат её шаблон с плейсхолдерами, напр.
    `ДОБАВИТЬКДАТЕ(<Дата>, <Тип>, <Количество>)`. Полный перечень функций — в
    [`tmp/1c-query-language.md`](../tmp/1c-query-language.md).
  - *Результат* — текстовое поле; по «ОК» текст возвращается в поле Условие (или
    добавляется новым полем в панель «Поля»).
- **Добавление произвольного поля.** Кнопка «+» в панели «Поля» открывает то же окно
  «Произвольное выражение»; по «ОК» выражение добавляется отдельным полем выборки.
- **Генератор SDBL.** Источник-виртуальная таблица рендерится как
  `РегистрСведений.<Имя>.СрезПоследних(<Период>, <Условие>) КАК <Псевдоним>`; при
  пустых параметрах — `СрезПоследних()`; поля выборки префиксуются псевдонимом
  виртуальной таблицы. Эталоны текста запроса — на скриншотах
  `tmp/meta/РегистрСведений`.

Затрагивает все слои: модель метаданных (флаг периодичности → виртуальные таблицы),
`QueryModel` и контракт сообщений (параметры виртуальной таблицы, произвольные
выражения), генератор SDBL, webview (дерево, два новых модальных окна, drag&drop в
конструкторе выражений). Остальные виртуальные таблицы регистров (Остатки, Обороты,
ОстаткиИОбороты, движения с субконто) — за рамками этой итерации.

#### 4.3. Виртуальные таблицы регистров накопления

Прямое продолжение 4.2 на регистры накопления — то, что 4.2 явно отложил. Переиспользует
ту же машинерию (виртуальные таблицы в дереве, окно «Параметры виртуальной таблицы», окно
«Произвольное выражение», диспетчеризация генератора). Объём:

- **Состав виртуальных таблиц по виду регистра.** Вид регистра (`RegisterType`:
  Остатки/Обороты) сохраняется парсером в `properties`. У любого регистра накопления есть
  ВТ `Обороты`; у регистра вида Остатки дополнительно — `Остатки` и `ОстаткиИОбороты`.
  Виртуальные таблицы показываются в дереве «База данных» отдельными строками рядом с
  регистром (`РегистрНакопления.<Имя>.Обороты`), как срезы регистров сведений.
- **Развёртка ресурсов.** Каждый ресурс `<R>` разворачивается в колонки ВТ: `Остатки` →
  `<R>Остаток`; `Обороты` → `<R>Оборот` (+ `<R>Приход`, `<R>Расход` у регистра вида
  Остатки); `ОстаткиИОбороты` → `<R>НачальныйОстаток`, `<R>КонечныйОстаток`, `<R>Оборот`,
  `<R>Приход`, `<R>Расход`. Измерения копируются как есть.
- **Параметры виртуальных таблиц.** Окно «Параметры виртуальной таблицы» параметрично по
  виду ВТ: `Остатки` — `Период` + `Условие`; `Обороты` — `НачалоПериода`, `КонецПериода`,
  `Периодичность` (выпадающий список), `Условие`; `ОстаткиИОбороты` — дополнительно
  `МетодДополнения` (выпадающий список Движения/ДвиженияИГраницыПериода).
- **Зависимость полей от периодичности.** Для `Обороты`/`ОстаткиИОбороты` набор полей
  зависит от выбранной `Периодичности` (Период/Запись/Регистратор/Секунда…Полугодие/Авто):
  чистый core-хелпер `accumPeriodFields` добавляет к измерениям/ресурсам соответствующие
  поля периода (`Период`, `Регистратор`, `НомерСтроки`, либо семейство `ПериодСекунда…
  ПериодГод` для Авто).
- **Генератор SDBL.** Источник-ВТ рендерится с позиционными параметрами по виду ВТ:
  `Остатки(<Период>, <Условие>)`, `Обороты(<Начало>, <Конец>, <Периодичность>, <Условие>)`,
  `ОстаткиИОбороты(<Начало>, <Конец>, <Периодичность>, <МетодДополнения>, <Условие>)`;
  `Периодичность`/`МетодДополнения` — голые слова SDBL. Эталоны — в спеке.

Спек: [`specs/2026-06-03-phase4-accum-virtual-tables-design.md`](superpowers/specs/2026-06-03-phase4-accum-virtual-tables-design.md)
План: [`plans/2026-06-03-phase4-accum-virtual-tables.md`](superpowers/plans/2026-06-03-phase4-accum-virtual-tables.md)

За рамками: регистр бухгалтерии (субконто), виртуальные таблицы регистра расчёта,
валидация выражений и обратный разбор (фаза 6).

### ✅ Фаза 5. Вкладки конструктора

Поверх стабильного ядра `QueryModel` и контракта сообщений — **по одной фиче на
вкладку**. Каждая вкладка расширяет `QueryModel` своей секцией, генератор SDBL
дорисовывает соответствующую часть текста в фиксированном порядке языка запросов:

```
ВЫБРАТЬ [РАЗРЕШЕННЫЕ] [РАЗЛИЧНЫЕ] [ПЕРВЫЕ n]
  <поля выборки>            ← Таблицы и поля (5.0), Группировка (5.1)
[ПОМЕСТИТЬ | ДОБАВИТЬ <ВремТаб>]  ← Дополнительно (5.3)
ИЗ <источники> [<СОЕДИНЕНИЕ> … ПО …]  ← Связи (5.5)
[ГДЕ <условия>]              ← Условия (5.2)
[СГРУППИРОВАТЬ ПО …]         ← Группировка (5.1)
[ДЛЯ ИЗМЕНЕНИЯ <таблицы>]    ← Дополнительно (5.3)
[ОБЪЕДИНИТЬ [ВСЕ] <след. запрос>]  ← Объединения/Псевдонимы (5.4)
[УПОРЯДОЧИТЬ ПО …] [АВТОУПОРЯДОЧИВАНИЕ]  ← Порядок (5.6)
[ИТОГИ … ПО …]              ← Итоги (5.7)
{ВЫБРАТЬ …} {ГДЕ …} {УПОРЯДОЧИТЬ ПО …} {ИТОГИ ПО …}  ← Построитель (5.9)
[ИНДЕКСИРОВАТЬ ПО [НАБОРАМ] …]  ← Индекс (5.10, при ПОМЕСТИТЬ)
… ; //// … ; УНИЧТОЖИТЬ …    ← Пакет запросов (5.8)
```

Вкладки конструктора 1С и статус: **Таблицы и поля** (готова, фазы 0–4),
Группировка (5.1), Условия (5.2), Дополнительно (5.3), Объединения/Псевдонимы (5.4),
Связи (5.5), Порядок (5.6), Итоги (5.7), Пакет запросов (5.8), Построитель (5.9),
Индекс (5.10). Технически вкладки реализуются как переключаемые панели в `TabsBar`/`App`,
общий `QueryModel` живёт в `queryStore`.

#### 5.1. Вкладка «Группировка»

Секция `СГРУППИРОВАТЬ ПО`. Поля делятся на **поля группировки** и **суммируемые поля**

### 🚧 Фаза 6. Обратный разбор текста запроса

Двунаправленность: из текста запроса SDBL восстанавливается визуальная модель
(`QueryModel`/`QueryDocument`/`BatchDocument`) — инверсия `sdblGenerator`. Существующий
запрос открывается из `.bsl` по ПКМ, редактируется в конструкторе и сохраняется обратно
в то же место.

**Архитектурное уточнение:** вместо tree-sitter в рантайме разбор реализован
**рукописным pure-TS парсером** (`src/core/query/sdblLexer.ts` + `sdblParser.ts`),
симметрично рукописному генератору. Грамматика `tmp/tree-sitter-bsl/grammars/sdbl` —
референс синтаксиса; tree-sitter остаётся необязательным тест-оракулом, MCP
`1c-md validate_query` — оракулом при сборе корпуса. Причины (несобираемый WASM,
несовместимость ABI, философия «ядро — pure-TS») — в спеке, раздел 2.

Подзадачи: **6.1** CLI извлечения корпуса из `.bsl` (`src/cli/extractQueries.ts`,

(все секции, виртуальные таблицы, объединения, пакеты) · **6.3** приёмочный прогон
корпуса (`src/cli/acceptQueries.ts`) · **6.4** починка разбора реальных запросов

ИМЕЮЩИЕ) · **6.5** фикстуры + 100% покрытие парсера · **6.6** команда «1С: Конструктор

#### ✅ 6.8. Верность существующей модели против конструктора

Свод расхождений `mismatch` для конструкций, уже представимых моделью. Прогресс
измерен оракулом 6.7. Реализовано:

- **R1. Автопсевдоним простого поля** — конструктор всегда даёт простому полю выборки
  `КАК <последний сегмент пути>`, если явный псевдоним не задан. **+231.**
- **R2. ПРАВОЕ СОЕДИНЕНИЕ сохраняется** — конструктор не нормализует правое соединение
  перестановкой источников в ЛЕВОЕ. Эффект раскрылся вместе с R5.
- **R4. Оператор `В`/`В ИЕРАРХИИ` без пробела перед списком значений** —
  `В (&Список)` → `В(&Список)`. **+136.** Подзапрос после `В` (многострочный) — 6.11.
- **R5. Скобки условия соединения** — одиночное условие `ПО (a = b)` оборачивается,
  составное с верхнеуровневым И/ИЛИ — без внешних скобок (`ПО (a) И (b)`). **+94.**
- **R3. Квалифицированное поле в `УПОРЯДОЧИТЬ ПО`** — парсер теперь читает полный
  точечный путь; `Псевдоним.Поле` сохраняется как у конструктора. **+6.**

#### ✅ 6.10. Форматер произвольных выражений (`ВЫБОР`, многострочные условия)

Самый крупный остаток. У конструктора 1С есть собственный «красивый вывод» для любых
выражений в `ГДЕ`, в условиях соединения и в полях выборки: он переносит длинные
`И`/`ИЛИ` на новые строки с отступом по глубине, оборачивает отдельные слагаемые в
скобки (`a` \n `И (b)`), раскладывает оператор `ВЫБОР … КОГДА … ТОГДА … ИНАЧЕ … КОНЕЦ`
(CASE), убирает/ставит пробелы по своим правилам. Мы же сейчас храним такие выражения
как сырой текст и отдаём почти как есть — отсюда расхождения.

Это рычаг по большей части из 437 расхождений: запросов с `ВЫБОР` и многострочными
условиями в `ГДЕ`/`ИМЕЮЩИЕ`/соединениях. Метаданные не нужны.

Реализован самодостаточный модуль `src/core/query/exprFormatter.ts`: переотрисовывает
**только структуру** (булево дерево `ИЛИ`/`И`/`НЕ`, оператор `ВЫБОР`, скобки OR-групп),
а текст листьев (сравнения, вызовы функций, `МЕЖДУ a И b`, `ЕСТЬ НЕ NULL`, …) сохраняет
дословным срезом исходника — это даёт нулевой риск регрессий листового текста. Лексер
и парсер не тронуты (форматер сам ре-токенизирует выражение и распознаёт `ИЛИ`/`НЕ`/
`ВЫБОР`/… по верхнему регистру). Подключён в `sdblGenerator`: `ГДЕ`/`ИМЕЮЩИЕ` (base 1),
поля выборки (value-слот), составные условия соединений `ПО` (base 2, по-конъюнктное
оборачивание). `needsFormatting` срабатывает только при наличии OR- или CASE-узла —
ранее принятые простые выражения остаются байт-в-байт.

Правила отступов (вычитаны по оракулу, проверены побайтно): OR — `ИЛИ` на base+2 (1-й
уровень) / +1 (глубже), группа в скобках; `ВЫБОР` — `КОГДА=E+1, ТОГДА=E+2, ИНАЧЕ=E+1,
КОНЕЦ=E`, где `E` = контентный отступ слота (+1 для boolean-слота).

**Итог 6.10:** принято **1392 → 1417**, mismatch 437 → 412, parse-exception 147
(без изменений), 0 регрессий принятых. Весь оставшийся остаток (412 mismatch + 147
parse-exception) учтён по классам в **6.12** (подзапросы вынесены в 6.11).

- План: [`plans/2026-06-11-phase6.10-expression-formatter.md`](superpowers/plans/2026-06-11-phase6.10-expression-formatter.md)

#### ✅ 6.11. Подзапрос в источнике «ИЗ» (вложенный запрос как узел модели)

1С разрешает писать в `ИЗ` не таблицу, а вложенный запрос: `ИЗ (ВЫБРАТЬ … ) КАК Данные`,
в том числе с `ОБЪЕДИНИТЬ` внутри. Модель источника была только таблицей, поэтому такие
запросы не парсились: в корпусе их **65, отклонялись все**.

Сделано: `SelectedTable` получил необязательное поле `subquery?: QueryDocument` —
источник-подзапрос стал полноценным узлом модели. `parseTableSource` поглощает
сбалансированную скобку, рекурсивно разбирает содержимое через `parseDocument`
(поддержка вложенного `ОБЪЕДИНИТЬ`), требует обязательный `КАК <алиас>`. `renderSource`
рендерит подзапрос реверсивно: `generateDocument` подзапроса реиндентируется на +1 таб,
`(` на первой строке, `) КАК <алиас>` на последней (пустая строка-разделитель
`ОБЪЕДИНИТЬ` → строка из одного таба, как у конструктора). Изменения гейтятся наличием
`subquery`/`(` — для запросов без подзапросов разбор и вывод байт-в-байт прежние.

**Итог 6.11:** все 65 подзапросов-источников теперь парсятся (0 parse-exception по этому
классу). Принято **1417 → 1444** (+27), parse-exception 147 → 94 (−53), mismatch 412 → 438
(+26 — подзапросы, которые парсятся, но чей вложенный текст ещё расходится по форматеру:
`ВЫБОР`/`В (ВЫБРАТЬ …)` внутри, отступ подзапроса-участника соединения → 6.12-C). **0
регрессий** ранее принятых.

Подзапрос после оператора `В (ВЫБРАТЬ …)` (94 случая) **вынесен в 6.12-C**: его отступ
контекстно-зависим (зависит от позиции `В` в произвольном выражении), завязан на форматер
6.10 и не сводится к чистому правилу; остаётся `custom`-выражением.

- Спек: [`specs/2026-06-11-phase6.11-from-subquery-design.md`](superpowers/specs/2026-06-11-phase6.11-from-subquery-design.md)

#### ✅ 6.12. Зачистка остатка приёмки (метаданно-независимые классы закрыты; остаток задокументирован)

**Цель — ноль.** Оракул `validate_query(input).query_text` детерминирован: это
канонический текст объекта `СхемаЗапроса` конструктора, один и тот же для одного input.
Раз конструктор принял текст (`valid: true`) и выдал `query_text`, значит у него **есть
модель** этого запроса — а значит её можно воспроизвести. Поэтому цель проекта — принять
**все 1976 валидных** (`report.json` пуст: mismatch = 0, parse-exception = 0). 112
oracle-invalid конструктор отвергает сам — у них нет эталона, они вне знаменателя.

**Итог 6.12 (коммиты `6.12.1`–`6.12.27`):** принято **1417 → 1717** (87% валидных),
**parse-exception 147 → 0**, mismatch **412 → 259**. Последняя серия `6.12.11`–`6.12.27`
(последовательные субагенты, по одному классу; гейт 6.7 + `npm run test:unit`, ноль
регрессий на каждом шаге) дала **+99** (1618 → 1717). Все *метаданно-независимые* классы,
сводимые к чистому правилу, **закрыты**; оставшиеся 259 — три ригорозно-доказанных
**неустранимых без доп. данных оракула** класса (см. ниже).

**Закрыто серией `6.12.11`–`6.12.27`** (каждый — oracle-фикс + курируемая фикстура
`test/fixtures/oracle/`):
- Скобки `(НЕ <поле>)` в ГДЕ при дословном хвосте; хвостовой пробел квирка `ЕСТЬ НЕ NULL`.
- Форматер `ВЫБОР`: **селекторная форма** `ВЫБОР <выр> КОГДА …`; `И` внутри `ТОГДА/ИНАЧЕ`
  не разрывает условие ГДЕ; снятие избыточных скобок ведущей `ИЛИ`-группы.
- **Сохранение порядка источников соединения** (seed не переупорядочивается по операнду
  условия — `renderFrom` берёт текстовый seed, а не таблицу из ПО).
- Разбор `Таблица.ТЧ.(поля)` (голые и квалифицированные имена) в ВЫБРАТЬ; `&Параметр` в
  `ИНДЕКСИРОВАТЬ ПО`/`УПОРЯДОЧИТЬ ПО`; **бесисточниковый ПОМЕСТИТЬ** (был пустой вывод).
- **Удаление ведущих нулей** в числах (`ДАТАВРЕМЯ(2000, 01, 01)`→`(2000, 1, 1)`) — широко
  нагруженное, **+28**. Литерал периода (`ДЕНЬ/МЕСЯЦ/…`) в верхнем регистре как аргумент
  даты-функции.
- `МЕЖДУ a И b` инлайн (внутренний `И` не принимается за конъюнкт); список `В (a, b)`
  сплющивается в одну строку.
- **`ГДЕ` останавливается на `ИТОГИ`/`ИНДЕКСИРОВАТЬ`/`ДЛЯ`/`УПОРЯДОЧИТЬ`/`ИМЕЮЩИЕ`**
  (`WHERE_STOP` был неполон → секции засасывались в последнее условие и выводились
  дословно с грязным отступом) — нагруженное, **+40**; плюс квалификация полей секций.

**Неустранимый остаток (259), задокументирован по критерию фазы:**
1. **Скобки условий — внутренний флаг конструктора (~86).** `ПО (a=b)` ¦ `ПО a=b`,
   `И (cond)` ¦ `И cond`, ведущая скобка OR-группы, `В (&X)` ¦ `В(&X)`. Зависит от того,
   построено ли условие реляционным редактором (→ скобки) или введено как произвольное
   выражение (→ без скобок) — **внутренняя классификация `СхемаЗапроса`, не восстановимая
   из канонического текста и не выводимая из схемы метаданных**. Гипотеза «оборачивать по
   разрешимости операндов» построена и **строго опровергнута**: 228 wrap / 111 bare при
   resolved|resolved, контрпример — самосоединение одного регистра (первое соединение bare,
   прочие wrap); все варианты предиката давали чистую регрессию приёмки.
2. **Квалификация полей по метаданным — ограничена покрытием схемы (~54).** `Поле` ¦
   `Таблица.Поле`, `* КАК Поле1`, имена источников для temp/`&Параметр`/подзапросных
   таблиц. Резолвер метаданных построен (`MetadataResolver`, опциональная инъекция в
   `parseBatch`, чистый путь байт-в-байт), но применимое множество на корпусе **пусто**:
   бара́е поля ссылаются на источники вне YAML-схемы (ВТ `ПОМЕСТИТЬ`, `&Параметр`,
   подзапросные псевдонимы) — резолвер корректно возвращает «неизвестно». `УПОРЯДОЧИТЬ ПО`
   тоже не чистое правило (114 принятых держат поле бара́м; принудительно — −7). Резолвер
   не закоммичен (приёмка не растёт; чистый путь сохранён).
3. **Контекстно-зависимый отступ + оракул-side преобразования.** Отступ подзапроса в
   value-слоте (`(ВЫБРАТЬ ПЕРВЫЕ 1`) и `КОГДА` во вложенном `ВЫБОР` расходятся **в обе
   стороны** (+1/−1 таб) по глубине контекста — не одно правило. Плюс оракул-side: пустой
   вывод для `ВЫБРАТЬ * ИЗ &Параметр`, переписывание агрегатов — делается конструктором из
   метаданных, которых у нас нет.

Дальнейший прогресс по классу 1 требует харвеста *внутреннего* представления соединения
конструктора (флаг «простое условие» vs «произвольное») — отдельная итерация сбора данных,
а не текстовое/схемное правило.

#### ✅ 6.13. Стандартные vs произвольные условия связи (скобки `ПО` + галочка «Произвольное»)

Класс скобок `ПО`, ошибочно помеченный в 6.12 неустранимым, **закрыт** по правилу,
подтверждённому конструктором 1С (скриншоты): при соединении двух таблиц **стандартное**
условие связи (`ЛевойТаблицы.Поле <оп> ПравойТаблицы.Поле`, задаётся мышкой в редакторе
связи) печатается **без скобок**; **произвольное** (параметр/константа/функция в операнде,
**перестановка операндов**, оба операнда одной таблицы, `ИЛИ`/`ВЫБОР`) — **в скобках** и
помечается галочкой «Произвольное». Перестановка операндов не меняет смысл, но переводит
условие в произвольное — конструктор не нормализует порядок, а классифицирует как-есть.

Правило **полностью выводится из модели** (без метаданных): нужны лишь псевдонимы источников.
STANDARD iff конъюнкт `ПО` — сравнение `<КореньЦепочки>.<путь> <cmp> <Присоединяемая>.<путь>`
(левый операнд — поле КОРНЯ цепочки `ИЗ`, правый — присоединяемой таблицы; чистые поля; оп
сравнения). Эмпирика по корпусу: 95.6% конъюнктов. Это опровергает «неустранимость» класса 1
из 6.12 — ключом была доменная подсказка пользователя.

- **6.13.1 (core):** модель `Join.conditions: JoinCondition[]` (per-conjunct `custom`-флаг);
  парсер `splitJoinConjuncts`+`classifyJoinConjunct` (по КОРНЮ цепочки `chainSeedAlias`);
  генератор — поконъюнктные скобки по флагу. **принято 1717 → 1758 (+41)**, mismatch 259 →
  218, 0 регрессий. Фикстуры `0087`–`0090`. Коммит `1590c3b`.
- **6.13.2 (webview):** вкладка «Связи» — строка на конъюнкт, галочка «Произвольное» из
  `conditions[i].custom`: запрос открывается с корректно расставленными галочками. Сеттеры
  store по `(joinIndex, condIndex)`, `ADD/REMOVE_JOIN_CONDITION`, +4 unit-теста (round-trip).
  accept:oracle без изменений (1758/0). Коммит `2770e8e`.

Остаток скобок `ПО` (≈21): temp-затравки (`ВТ_*`), соединения с табличными частями,
избыточные внешние скобки — реконструкция дерева соединений конструктором, документируется.

## Ключевые архитектурные решения

- **Отдельное расширение, свой парсер метаданных** — независимость от

- **YAML на диске как контракт** парсера — человекочитаемый артефакт верификации,
