# Фаза 8.4. Локальная семантическая валидация открытия (реализация 8.2) — дизайн

← [Дорожная карта](../../ROADMAP.md) · [Фаза 8](../../PHASE_8.md)

Дата: 2026-06-27. Реализация рекомендации [исследования 8.2](2026-06-23-phase8.2-validation-research-design.md).
Опирается на парсер Фаз 6–7 (`parseBatch`) и консолидированный кэш метаданных Фазы 7.2.

## 1. Проблема (из 8.2)

Критерий «открывается ли запрос конструктором» — **чисто синтаксический**
(`validateBatch.ts → tryParseBatch → parseBatch` не бросил → открываем). Парсер не знает
метаданных, поэтому запрос на **несуществующую таблицу** открывается. Эталон из требований:

```
ВЫБРАТЬ Валюты.Ссылка КАК Ссылка, Валюты.Наименование КАК Наименование
ИЗ Справочник.Валюты1 КАК Валюты
  ЛЕВОЕ СОЕДИНЕНИЕ Справочник.БанковскиеСчета КАК БанковскиеСчета
  ПО Валюты.ОсновнаяВалюта = БанковскиеСчета.Ссылка
```

`Справочник.Валюты1` не существует — текст **не должен открываться**; с `Справочник.Валюты`
— открывается. Исследование 8.2 показало, что MCP `validate_query` ловит это как
`{(5,2)}: Таблица не найдена "Справочник.Валюты1"`. **MCP в рантайме не используется** —
проверку воспроизводим локально по кэшу метаданных.

## 2. Объём (что проверяем) и границы (что НЕ проверяем)

Ведущий принцип: **ложное срабатывание (отказ открыть валидный запрос) хуже, чем пропуск
невалидного**. Поэтому реализуем только проверки, выводимые из кэша надёжно и без ложных
срабатываний; остальное (из §4 исследования «не проверяет») оставляем явной границей.

### 2.1. В объёме

1. **Существование таблицы по полному имени `Тип.Имя`** (реальные объекты и виртуальные
   таблицы регистров). Источник проверяется ⇔ его `fullName` содержит точку И первый
   сегмент — распознаваемый префикс типа метаданных (`TYPE_PREFIXES`, см. §3). Резолв —
   через `MetadataResolver` (реальная / виртуальная / каноническая по ВЕРХ-регистру). Нет
   резолва → `Таблица не найдена "<fullName>"` с позицией `{(строка, столбец)}` (best-effort).
   Покрывает (сверено отчётом 8.2): опечатку имени (A#16, `Валюты1`), неверный префикс типа
   (A#17, `Документ.X` для справочника), несуществующий объект (A#20–23), неприменимый срез
   регистра (D#13/14/28/30, напр. `.Остатки` у оборотного → не найдено), табличную часть как
   источник (B#4/5, 3-сегментное имя через `canonicalFullName`).

2. **Повтор явного псевдонима поля выборки** в одном запросе (B#13:
   `… КАК Поле1, … КАК Поле1` → `Повторяющийся псевдоним "Поле1"`). Чисто модельная проверка,
   метаданные не нужны, работает даже без кэша. Срабатывает ТОЛЬКО на двух ЯВНЫХ (`alias`,
   не синтезированных) одинаковых (регистронезависимо) псевдонимах — синтезированные
   псевдонимы дедуплицирует генератор (6.16.24), их не трогаем.

Проверка рекурсивна: обходятся все `QueryModel` пакета — участники ОБЪЕДИНЕНИЯ, источники-
подзапросы (`ИЗ (ВЫБРАТЬ …)`), подзапросы условий (`… В (ВЫБРАТЬ …)`). Соединённые таблицы
уже лежат в `model.tables` (там же, где и затравка) — отдельного обхода `joins` не нужно.

### 2.2. Границы (НЕ проверяем — воспроизводим §4 исследования)

- **Поля, реквизиты, навигация через точку** — НЕ проверяем. Причина инженерная и
  доказанная кодом: стандартные поля (`Ссылка`/`Код`/`Наименование`/`ПометкаУдаления`/
  `Предопределённый`/`ЭтоГруппа`) в `MetaTable.fields` объектных таблиц **отсутствуют** —
  они синтезируются только при развёртке `*` (`yamlLoader.parsedObjectToMetaTable` кладёт
  лишь реквизиты). Проверка полей по `MetaTable.fields` дала бы ложное «Поле не найдено» на
  каждом реальном запросе. Корректная проверка полей потребовала бы синтеза стандартных
  полей по виду таблицы + разыменования ссылочных реквизитов (навигации), которой в
  `MetadataResolver` нет. Это отдельная крупная возможность — вынесено в задел (см. §6).
- **Голое имя без точки** — трактуем как ВТ/подзапрос/CTE, не проверяем (auto: правило
  «есть точка» само пропускает; временные таблицы `ПОМЕСТИТЬ` адресуются голым именем).
- **Типы значений `&Параметр` и параметров ВТ; состав/арность параметров ВТ; число колонок
  ОБЪЕДИНЕНИЯ; согласованность группировки; значения `ЗНАЧЕНИЕ(Перечисление.…)`** — НЕ
  проверяем (часть не выводится из кэша надёжно, часть — риск ложных срабатываний на `*`).
- **Разметка `{…}`** — прозрачна (парсер уже её обрабатывает; на состав таблиц не влияет).
- **Регистр** — имена резолвятся регистронезависимо (`canonicalFullName` по ВЕРХ-регистру);
  английские префиксы (`Catalog.`/`Document.`) парсер уже переводит в русские до модели.

### 2.3. Fail-open (ключевая защита от ложных срабатываний)

Если резолвер не построен или кэш пуст (`tables.length === 0`) — семантическая проверка
**пропускается целиком** (поведение прежнее, открываем). Так частичный/отсутствующий кэш
не блокирует валидные запросы. Кэш-дерево (`metadataTree`) — консолидированная модель
(`modelCache`), все полные имена таблиц в ней присутствуют, поэтому проверка существования
таблиц надёжна, когда кэш есть.

## 3. Архитектура

Логика — pure-TS в `core`, без зависимостей от webview/vscode. Вывод оракула не меняется
(новая проверка работает ПОСЛЕ парсинга, генератор не трогаем) → золотой оракул и регрессия
корпуса 1976/1976 остаются байт-в-байт.

- **`src/core/query/semanticValidator.ts`** (новый):
  - `interface SemanticError { message: string; line?: number; col?: number; fullName?: string }`.
  - `validateBatchSemantics(doc: BatchDocument, resolver: MetadataResolver | undefined, text: string): SemanticError[]`.
    `resolver === undefined` → `[]`. Иначе обход всех `QueryDocument`/`QueryModel`, проверки §2.1.
    Позиция вычисляется по `tokenize(text)` поиском последовательности сегментов имени
    (`ident . ident …`, регистронезависимо); не нашли — позиция опускается.
  - `TYPE_PREFIXES` (ВЕРХ-регистр) — фиксированный набор запрашиваемых видов: `СПРАВОЧНИК`,
    `ДОКУМЕНТ`, `РЕГИСТРНАКОПЛЕНИЯ`, `РЕГИСТРСВЕДЕНИЙ`, `РЕГИСТРБУХГАЛТЕРИИ`, `РЕГИСТРРАСЧЕТА`,
    `ПЕРЕЧИСЛЕНИЕ`, `ПЛАНСЧЕТОВ`, `ПЛАНВИДОВХАРАКТЕРИСТИК`, `ПЛАНВИДОВРАСЧЕТА`, `ПЛАНОБМЕНА`,
    `БИЗНЕСПРОЦЕСС`, `ЗАДАЧА`, `КОНСТАНТА`. Исключены `КритерийОтбора`/`Последовательность`/
    `ЖурналДокументов`/`ТабличнаяЧасть`/`ВременнаяТаблица` — параметризованные/голые/3-сегментные
    источники, проверка которых дала бы ложные срабатывания (ТЧ покрыта `canonicalFullName`).

- **`src/core/metadata/buildModelResolver.ts`** (новый): `buildResolverFromTables(tables: MetaTable[]):
  MetadataResolver` — in-memory зеркало `buildYamlResolver` (те же три карты: реальные по
  `fullName`, виртуальные по `fullName`, канонические по ВЕРХ-регистру, ТЧ в канонической
  карте). `buildYamlResolver` рефакторится в делегата (`loadMetadataFromYaml` →
  `buildResolverFromTables(model.tables)`) — единый источник правды, без дублирования.

- **`src/core/query/validateBatch.ts`**: новый `tryOpenBatch(text, resolver?, opts?): ParseAttempt`
  — `tryParseBatch` + при успехе `validateBatchSemantics`; первая семантическая ошибка →
  `{ ok:false, error }`. `validateBatchText(text, resolver?)` — добавляется необязательный
  резолвер для проверки при «ОК». Существующие `tryParseBatch`/`validateBatchText` без
  резолвера сохраняют прежнее поведение (обратная совместимость, синтаксис-only).

- **`src/webview/App.tsx`**: ссылка `metaTablesRef` обновляется на `metadataTree` (наряду с
  `SET_METADATA`). Резолвер строится из неё (`buildResolverFromTables`, только при непустых
  таблицах). `loadModel` → `tryOpenBatch(text, resolver, { preserveComments:true })`;
  семантическая ошибка показывается тем же оверлеем `load-error` (заголовок обобщается:
  «Не удалось открыть запрос»). «ОК» → `validateBatchText(batchText, resolver)`. Порядок
  сообщений гарантирует, что `metadataTree` приходит до `loadModel` (`panel.ts`).

Сообщение об ошибке — в стиле эталона: `{(строка, столбец)}: Таблица не найдена "<fullName>"`
(позиция при наличии), иначе `Таблица не найдена "<fullName>"`.

## 6. Задел (вне объёма)

- **Проверка полей/навигации**: синтез стандартных полей по виду таблицы (как
  `buildSelectAllModel`) + разыменование ссылочных реквизитов (рекурсивная навигация) →
  расширение `MetadataResolver` методом резолва поля. Высокий риск ложных срабатываний —
  отдельная подфаза со сверкой по корпусу.
- Число колонок ОБЪЕДИНЕНИЯ, согласованность группировки, значения перечислений — после
  поля/навигации, по эталону §§2.E/2.B исследования.
