## Зачем

Подфазы 7.3 и 7.4 сняли симметричные визуальные описи реального «Конструктора запроса»
1С и нашего webview-конструктора на одних и тех же 10 сложных запросах корпуса. Накоплен
материал для прицельного диффа. 7.5 — **аналитическая подфаза**: превратить две описи в
(1) структурированный дифф, (2) перечень доработок с рекомендациями, (3) каталог
возможных UI-ошибок и (4) методологию проверки UI на полном корпусе. Кода 7.5 **не
пишет и не исполняет** — её выход является входом в реализацию (7.6+).

**Целевая установка (решение ревью).** Реальный конструктор — *ориентир паритета*, но не
строгий пиксель-эталон. Наши добавки (**«Построитель»**, **«Порядок»**, 4-й тип
**«Уничтожение ВТ»**, кнопка **«Обновить кэш»**, табличная форма **«Связи»**) —
**намеренные фичи** этого инструмента и сохраняются. Закрываем только настоящие пробелы
паритета и дефекты, не ломая value-add.

## Раздел 1. Дифф 7.3 ↔ 7.4

Метод: пройти описи по каркасу окна и по каждой вкладке, каждое расхождение пометить
тегом `✓ совпадает` / `⚠ пробел паритета` / `★ намеренная добавка (сохраняем)`.

### Каркас окна

| Элемент | Реальный (7.3) | Наш (7.4) | Тег |
|---|---|---|---|
| Строка вкладок | `Таблицы и поля · [Связи] · Группировка · Условия · Дополнительно · Объединения/Псевдонимы · [Индексы] · Итоги · [Пакет]` | `Таблицы и поля · [Связи] · Группировка · Условия · Дополнительно · [Индекс] · Объединения/Псевдонимы · Порядок · Итоги · Построитель · [Пакет]` | ⚠ порядок + ⚠ имя «Индекс/Индексы» + ★ «Порядок»/«Построитель» |
| Контекст пакета/оператора | нижние дропдауны **«Редактируемый запрос:» / «Редактируемый оператор:»** | правый вертикальный стрип имён запросов пакета | ★ (стрип — наш механизм) + ⚠ (нет явной подписи «оператор объединения») |
| Нижняя панель | **Запрос · ОК · Отмена · ?** на всех вкладках | одна **«Запрос»**; **Вставить/Отмена** — внутри панели «Поля» вкладки «Таблицы и поля» | ⚠ нет постоянных ОК/Отмена; кнопки подтверждения «спрятаны» в одну вкладку |
| Панель кэша | — | **«Обновить кэш»** + статус под вкладками | ★ намеренная (7.2) |

### По вкладкам (сводка тегов; детали — в самих описях)

- **Таблицы и поля** — `✓` три панели База данных → Таблицы → Поля, переносы, «Еще ▾».
  Расхождение размещения Вставить/Отмена учтено в каркасе.
- **Связи** — `⚠`: реальный — дерево «ведущая→присоединённая» + колонка **типа связи**
  (Левое/Правое/Полное/Внутреннее); наш — **плоская таблица** (`№ · Таблица 1 · Все ·
  Таблица 2 · Все · П. · Условие · оператор · значение`). Тип связи у нас выражается
  парой флажков «Все» (внешнее соединение слева/справа). `★` форма таблицы.
- **Группировка** — `✓` структурно совпадает (Поле группировки + флажок «несколько
  группировок» + Суммируемое поле/Функция).
- **Условия** — `✓` по смыслу (дерево «Поля» → таблица условий).
- **Дополнительно** — `✓` Выборка записей + Тип запроса + Таблицы/Таблицы для изменения;
  `★` 4-й тип «Уничтожение ВТ» (реальный — 3 типа).
- **Индекс(ы)** — `✓` структура (Имя/Уникальный, поля индекса, ↑/↓); `⚠` имя в ед. числе.
- **Объединения/Псевдонимы** — `✓` Запросы → Имя поля → колонка псевдонимов.
- **Итоги** — `✓` парна реальной (`ИТОГИ … ПО …`).
- **Порядок** — `★` нашей вкладки в реальном нет (упорядочивание там в другом месте).
- **Построитель** — `★` нашей вкладки в реальном нет (источник данных в стиле СКД).
- **Пакет запросов** — `✓` список запросов пакета + командная панель + переключение
  активного запроса.

**Итог раздела 1:** настоящих `⚠`-пробелов четыре — форма «Связи» (презентационная),
нижняя панель (ОК/Отмена + контекст оператора), имя «Индекс»→«Индексы», порядок вкладок.
Всё прочее — либо совпадает, либо намеренная добавка.

## Раздел 2. Предлагаемые доработки (только пробелы паритета)

Каждый пункт: *проблема → рекомендация → обоснование*. Финальное «делать/нет» — на ревью
бэклога; здесь — рекомендация по умолчанию.

1. **Имя вкладки «Индекс» → «Индексы».**
   *Рек.:* переименовать (мн. число, как в реальном). *Обоснование:* нулевой риск,
   мгновенный паритет надписи. **Дёшево.**

2. **Порядок вкладок.** Сейчас наши добавки вклинены между общими вкладками.
   *Рек.:* выстроить общие вкладки в порядке реального (`… Дополнительно · Объединения ·
   [Индексы] · Итоги · [Пакет]`), а наши `Порядок`/`Построитель` сгруппировать в конце
   (перед/после «Пакет» — определить в плане). *Обоснование:* пользователь, знакомый с
   1С, находит вкладки на привычных местах; добавки визуально отделены. **Дёшево.**

3. **Нижняя панель: постоянные «ОК»/«Отмена».** Сейчас подтверждение/отмена живут в
   панели «Поля» одной вкладки.
   *Рек.:* вынести **ОК/Отмена** (наш аналог Вставить/Отмена) в нижнюю панель, видимую на
   всех вкладках, рядом с «Запрос». *Обоснование:* в реальном они всегда под рукой; сейчас
   на не-первой вкладке нет очевидного способа подтвердить. **Средне.**

4. **Контекст оператора объединения в нижней панели.** Реальный показывает «Редактируемый
   запрос/оператор»; у нас контекст пакета — правый стрип, но оператор объединения явно
   не подписан.
   *Рек.:* добавить текстовую подпись активного запроса/оператора в нижнюю панель
   (стрип сохраняем как механизм выбора). *Обоснование:* при объединениях/пакете теряется
   контекст «к какому запросу относится текущая вкладка». **Средне.**

5. **«Связи» — ясность типа соединения.** Презентационно отличается от дерева реального;
   тип связи закодирован двумя флажками «Все».
   *Рек.:* форму-таблицу **сохранить** (value-add), но проверить, что любой тип
   (Внутреннее/Левое/Правое/Полное) однозначно выражается и читается; при неоднозначности
   добавить явный индикатор/тултип типа. *Обоснование:* функционально таблица полна; диф —
   читаемость, а не возможности. **Средне (после проверки).**

Намеренно **не трогаем**: «Построитель», «Порядок», тип «Уничтожение ВТ», «Обновить кэш».

## Раздел 3. Каталог возможных UI-ошибок

Часть кандидатов **наблюдаема прямо на снятых скриншотах 7.4** (приведены ниже как seed);
остальное ищется систематически методом Раздела 4. Каждый кандидат: *симптом → где видно →
как подтвердить*.

### Seed (замечено на скриншотах 7.4)

- **E1. Обрезка текста в колонках «Связи».** Колонка «Таблица 2» узкая —
  `ВидыЗаказНарядовПоряд…` обрезано без тултипа. *Где:* `…ЗаказПокупателя…_89/02-связи.png`.
  *Подтвердить:* проверить ширины/overflow ячеек на запросах с длинными именами таблиц.
- **E2. Дубли полей в списках.** На вкладке «Порядок» `ЗаказНаряд.Дата` встречается
  дважды. *Где:* `…ЗаказПокупателя…_89/08-порядок.png`. *Подтвердить:* сверить список
  доступных полей с `QueryModel` — нет ли повторов узлов (вероятно, поле из основной
  таблицы + из соединённой/реквизита даёт коллизию имени).
- **E3. «Построитель» всегда виден и пуст.** Вкладка показывается на каждом запросе,
  целевой список пуст («Перетащите поля…»), под-вкладки `Поля/Условия/Порядок/Итоги`
  дублируют общие вкладки `Группировка/Условия/Порядок/Итоги`. *Где:*
  `…ЗаказПокупателя…_89/10-построитель.png`. *Подтвердить:* решить, не вводит ли дубль в
  заблуждение; кандидат — прятать под условие применимости (как «Связи»/«Индекс»).
- **E4. Дублирование упорядочивания.** Вкладка «Порядок» и под-вкладка «Построитель →
  Порядок» — два места для одной сущности. *Подтвердить:* проверить, синхронизированы ли
  они и не расходятся ли состояния.
- **E5. Правый вертикальный стрип: возможная обрезка/перекрытие.** Длинные имена
  (`ВременнаяТаблицаКурсыВалютСрезПоследних`) в `vertical-rl` при высоте окна ~1000px
  близки к краю. *Подтвердить:* проверить клиппинг при многих/длинных именах запросов
  пакета и перекрытие с контентом вкладки.

### Систематически проверяемые классы дефектов (ищет Раздел 4)

- **D-парсинг:** `pageerror`/исключение webview при `loadModel` (в 7.4 на 10 запросах — 0,
  но корпус шире).
- **D-вкладки:** видимый набор вкладок не соответствует фиче-вектору запроса (например
  «Связи» при 1 таблице или её отсутствие при >1).
- **D-полнота:** поле/таблица/условие из `QueryModel` не отрисованы в UI (потеря данных).
- **D-пустые панели:** обязательная панель вкладки пуста при наличии данных для неё.
- **D-вёрстка:** обрезка текста (overflow без тултипа), перекрытие, нулевая/отрицательная
  ширина колонок, горизонтальный скролл за пределы окна.
- **D-дубли:** повторяющиеся узлы в списках полей (как E2).

## Раздел 4. Методология проверки UI на полном корпусе

Корпус — `tmp/query1c/` (~17 934 файла). Цель пользователя: «проверить на полном корпусе
и не упустить недочётов». Прогонять 18k×N скриншотов вручную нереалистично и не нужно —
закладываем **покрытие по фичам запроса** с автоматическими инвариантами.

### 4.1. Фиче-вектор запроса

Для каждого файла корпуса разобрать текст обратным парсером Фазы 6 (`parseBatch` →
`QueryModel`) и извлечь булев/числовой вектор признаков, которые управляют видом UI:

- число таблиц (1 / >1), наличие соединений и их **типы** (Внутр./Левое/Правое/Полное);
- пакет (>1 запроса), временные таблицы (Создание/Добавление/Уничтожение ВТ), индексы;
- группировка, итоги (`ИТОГИ`), объединения (`ОБЪЕДИНИТЬ[ВСЕ]`), упорядочивание;
- подзапросы, виртуальные таблицы (СрезПоследних/Остатки/Обороты…), параметры (`&`);
- выражения `ВЫБОР…`, агрегатные функции, «Первые N», «Без повторяющихся».

Вектор покрывает ровно те оси, от которых зависит набор вкладок и содержимое панелей.

### 4.2. Классы эквивалентности и выборка

- Сгруппировать корпус по **комбинации признаков** (классы эквивалентности). Большинство
  18k запросов схлопнется в небольшое число классов.
- Из каждого класса взять **представителей** (≥1; для редких/сложных комбинаций — больше).
  Это даёт выборку в сотни, а не 18k запросов, при **гарантии**, что ни одна комбинация
  возможностей не пропущена.
- Зафиксировать **карту покрытия**: класс → сколько запросов в корпусе → сколько взято в
  выборку. Любой непокрытый класс — явный пробел (логируется, не замалчивается).

### 4.3. Автоматические инварианты (без ручного просмотра каждого кадра)

Расширить harness `tooling/our-constructor/` (приём 7.4): на каждом запросе выборки —
загрузить, обойти видимые вкладки и проверить ассерты, отражающие классы дефектов
Раздела 3:

- нет `pageerror`/исключений webview;
- видимый набор вкладок == ожидаемый по фиче-вектору;
- все поля/таблицы/условия из `QueryModel` присутствуют в DOM (D-полнота);
- нет пустых обязательных панелей при наличии данных (D-пустые);
- нет переполнения/обрезки (`scrollWidth>clientWidth` в ячейках без тултипа), нет
  горизонтального скролла окна (D-вёрстка);
- нет дублей узлов в списках полей (D-дубли).

Скриншот сохраняется **только** для запросов с проваленным ассертом (триаж), плюс по
одному эталонному кадру на класс. Так «не упустить недочёты» = «каждый класс прошёл
инварианты, провалы отскриншочены».

### 4.4. Отчёт

- Сводка: классов всего / покрыто / провалов по типам дефектов; ссылки на триаж-кадры.
- (Опционально, позже) **оракул-слой**: сверка «наш vs реальный» на под-выборке против
  живого 1С (драйвер 7.3) — структурный или скриншотный дифф. В 7.5 только закладывается
  как будущий слой, не реализуется.
