# Извлечение запросов из XML-макетов СКД (`<query>`)

**Дата:** 2026-06-13
**Статус:** утверждён, готов к планированию реализации
**Контекст:** доработка шага 4 в [`docs/corpus-testing.md`](../../corpus-testing.md) — извлечение запросов из конфигурации.

## Проблема

`npm run extract` (`src/cli/extractQueries.ts`) сканирует только `*.bsl` и
находит литералы запросов в коде. Много эталонных запросов лежит в XML-макетах
систем компоновки данных (СКД) — в элементе `<query>…</query>`, например
`src/cf/Reports/Задачи/Templates/ОсновнаяСхемаКомпоновкиДанных/Ext/Template.xml`.
Эти запросы не попадают в корпус, хотя они валидны и нужны для тестирования
конструктора.

В XML текст запроса хранится с экранированием спецсимволов XML-сущностями
(`&lt;` → `<`, `&gt;` → `>`, `&amp;` → `&`). Чтобы запрос совпал с тем, как он
выглядит в `.bsl`, при извлечении сущности надо декодировать обратно.

## Решения (утверждено)

- **Область сканирования:** только поддерево `CONFIG_DIR/Reports/`. На текущей
  конфигурации — 18 блоков `<query>` в 18 файлах под `Reports/` (по одному на файл).
- **Интеграция:** встроить в существующую команду `npm run extract` (а не
  отдельная команда). `extract` за один проход собирает и `.bsl`, и XML.
- **DCS-специфика (`РАЗРЕШЕННЫЕ`, `{…}` пользовательские настройки):** извлекать
  **дословно**, ничего не вырезать. Живой оракул (`validate_query`) принимает
  такой синтаксис и возвращает нормализованный `query_text` (в т.ч. с
  достроенными `КАК ПолеN` внутри `{…}`), поэтому такие запросы штатно проходят
  `harvest → golden` и тестируются конструктором наравне с `.bsl`. Расхождения
  конструктора всплывут как обычные записи в `ERRORS_DIR`, а не спрячутся.

## Архитектура

Всё — в `src/cli/extractQueries.ts`. Две новые чистые функции (без I/O,
юнит-тестируемые) и точечная правка `run()`.

### `unescapeXmlEntities(s: string): string`

Один проход слева направо одним регэкспом, декодирующий:

| Сущность | Символ |
|---|---|
| `&lt;` | `<` |
| `&gt;` | `>` |
| `&amp;` | `&` |
| `&quot;` | `"` |
| `&apos;` | `'` |
| `&#nn;` | по десятичному коду |
| `&#xHH;` | по шестнадцатеричному коду |

Регэксп вида `/&(amp|lt|gt|quot|apos|#x?[0-9a-fA-F]+);/g` с заменой через
таблицу/разбор кода. Проход слева направо корректно обрабатывает `&amp;lt;`:
сначала матчится `&amp;` → `&`, остаток `lt;` остаётся текстом, итог — литерал
`&lt;`, а не `<`.

На текущей конфигурации реально встречаются только `&amp;`, `&lt;`, `&gt;`;
остальные сущности декодируются защитно (на случай других конфигураций).

### `extractQueriesFromXml(xmlSource: string): ExtractedQuery[]`

- Находит каждый блок `<query>…</query>`. Это безопасно регэкспом
  `/<query>([\s\S]*?)<\/query>/g`: внутри текста запроса любой `<` всегда
  экранирован как `&lt;`, поэтому `</query>` не может встретиться в теле.
- Для каждого блока: декодирует тело через `unescapeXmlEntities`, вычисляет
  1-based номер строки открывающего тега `<query>` → `lineStart`.
- Оставляет только блоки, проходящие существующий `startsWithQueryKeyword`
  (начинаются с `ВЫБРАТЬ`/`УНИЧТОЖИТЬ`).
- Тело отдаётся **дословно** (без trim) — как и `.bsl` отдаёт распайпленный
  литерал без обрезки.

Возвращает тот же тип `ExtractedQuery { text, lineStart }`, что и BSL-ветка.

### Правка `run()`

После прохода по `*.bsl` (весь `cfRoot`, как сейчас) добавить проход по `*.xml`
**только** под `path.join(cfRoot, 'Reports')`:

- если каталог `Reports` не существует — тихо пропустить (другие конфигурации);
- иначе `walk(reportsDir, '.xml')`, для каждого файла `extractQueriesFromXml`;
- использовать **тот же** `seen`-set дедупа по `q.text` и **ту же** схему имён
  выходных файлов `${rel}_${idx + 1}.txt`, где `rel` — путь относительно
  `cfRoot`. Идентичный `.bsl`-запросу XML-запрос не пишется повторно.

`found` / `uniqueWritten` в финальном логе учитывают обе ветки.

## Поток данных

`*.xml (Reports/)` → `extractQueriesFromXml` → `unescapeXmlEntities` →
`ExtractedQuery.text` → дедуп по `seen` → `QUERY_CORPUS_DIR/<rel>_<idx>.txt` →
(далее существующий `harvest` → `oracle/golden.jsonl` → `accept:oracle`).

## Обработка ошибок / краевые случаи

- Нечитаемый XML-файл — `try/catch` вокруг `readFileSync`, пропуск (как в
  BSL-ветке).
- Файл без `<query>` — `extractQueriesFromXml` вернёт `[]`.
- Несколько `<query>` в одном файле — каждый получает свой `idx`.
- Каталог `Reports/` отсутствует — XML-проход пропускается, поведение `.bsl`
  не меняется (важно для совместимости с дефолтным gate).

## Тестирование (TDD)

Юнит-тесты (новый `test/unit/extractXmlQueries.test.ts` или дополнение к
существующему тесту экстрактора):

- `unescapeXmlEntities`: каждая сущность по отдельности; приоритет `&amp;lt;` →
  `&lt;`; десятичный и шестнадцатеричный numeric; строка без сущностей — без
  изменений.
- `extractQueriesFromXml`: один `<query>`; несколько `<query>` в одном
  источнике; теги, не являющиеся запросом, игнорируются; блок, не начинающийся
  с `ВЫБРАТЬ`, отбрасывается; корректный `lineStart`.
- Round-trip на реальном файле-фикстуре
  (`src/cf/Reports/Задачи/Templates/ОсновнаяСхемаКомпоновкиДанных/Ext/Template.xml`):
  извлечённый текст содержит `<`, `>`, `&` вместо сущностей и начинается с
  `ВЫБРАТЬ РАЗРЕШЕННЫЕ`.

## Документация

Одна строка в `docs/corpus-testing.md`, Шаг 4: `extract` дополнительно
извлекает `<query>` из `Reports/**/*.xml` (с декодированием XML-сущностей).

## Вне области (YAGNI)

- Сканирование `<query>` вне `Reports/` (Catalogs и пр.).
- Вырезание/нормализация DCS `{…}` или `РАЗРЕШЕННЫЕ`.
- Извлечение из других тегов (`<dataSource>` содержит только имена).
- Отдельная команда `extract:xml`.
- Пересборка закоммиченного gate (`corpus:snapshot`) — выполняется осознанно
  отдельно, когда конфигурация репозитория становится эталоном.
