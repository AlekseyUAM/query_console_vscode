# Спек — Фаза 6.7. Golden-оракул корпуса (конструктор как источник истины)

Дата: 2026-06-11. Источник задач: `tmp/draft.md` + диалог брейншторма.
Принцип итерации: спек → план → реализация по TDD. Ядро — pure-TS.

## 1. Контекст и проблема

Фаза 6 добавила обратный разбор (`parseBatch`/`generateBatch`). Приёмка корпуса
(`acceptQueries.ts`) сейчас использует критерий **самосогласованности**: запрос принят,
если `out1 = generateBatch(parseBatch(t0))` не бросил исключение и `out1 === out2`
(неподвижная точка). По этому критерию из 2088 запросов 1864 «приняты», 224 отклонены
(213 parse-exception, 11 not-idempotent).

Этот критерий **слаб**: «принятый» (идемпотентный) запрос всё равно может расходиться с
тем, что реально выдаёт конструктор 1С. Пример, подтверждённый оракулом:

```
вход:        УПОРЯДОЧИТЬ ПО ДатаВерсии
конструктор: УПОРЯДОЧИТЬ ПО ЗагруженныеВерсииАдресныхСведений.ДатаВерсии
```

и `ПРАВОЕ СОЕДИНЕНИЕ`, которое конструктор сохраняет, а наш генератор переворачивает в
`ЛЕВОЕ` со сменой источников.

## 2. Новый источник истины: `validate_query.query_text`

MCP-инструмент `1c-md validate_query` доработан: возвращает не только `valid`, но и
`query_text` — текст, который выдаёт объект `СхемаЗапроса` после разбора входного текста.
Это **канонический текст конструктора**. Текст запроса в конфигурации мог быть написан
руками и отличаться от канонического; `СхемаЗапроса` приводит его к канону.

**Новый критерий верности проекта:** для каждого запроса корпуса должно выполняться

```
generateBatch(parseBatch(input)) === validate_query(input).query_text
```

Это строго сильнее самосогласованности и ловит «принятые-но-неверные».

MCP нужен **только на этапе разработки/тестов**. Итоговое расширение автономно: рантайм —
только pure-TS `parseBatch`/`generateBatch`, без сети и без 1С-базы. `mcpClient.ts` и
`harvestOracle.ts` — CLI-инструменты разработчика (как `acceptQueries.ts`/`extractQueries.ts`),
в бандл расширения не попадают.

## 3. Транспорт MCP

Сервер `1c-md` — HTTP MCP (`.mcp.json`: `http://host.docker.internal/sslplus/hs/mcp/`).
Проверено: `tools/call` работает без сессионного handshake; ответ — JSON-RPC, в
`result.content[0].text` лежит JSON-строка `{ valid, message, query_text }`. В
`query_text` табы закодированы как `	`, переводы строк как `\n` (раскодируются
штатным `JSON.parse`).

## 4. Архитектура (4 изолированных юнита)

### 4.1. `src/cli/mcpClient.ts` — транспорт

```ts
export interface ValidateQueryResult { valid: boolean; message: string; query_text: string; }
export function readMcpUrl(): string;                      // из .mcp.json (1c-md.url)
export async function validateQuery(text: string, url?: string): Promise<ValidateQueryResult>;
```

Чистый транспорт: POST JSON-RPC `tools/call`, разбор вложенного JSON, нормализация
`query_text` (CRLF→LF, снятие BOM, снятие хвостового перевода строки — симметрично
`sdblGolden.ref()`). Не знает про корпус. Тестируется с мок-`fetch`.

### 4.2. `src/cli/harvestOracle.ts` — сбор эталонов

Читает `tmp/query1c/*.txt`, для каждого вызывает `validateQuery` (с ограничением
параллелизма и ретраями), дописывает строку в `tmp/query1c/oracle/golden.jsonl`.
**Резюмируемость:** при повторном запуске пропускает уже собранные `file` (если нет
`--force`). Прогресс в stderr.

### 4.3. `src/cli/oracleAccept.ts` — приёмка против оракула

Чистая, тестируемая функция:

```ts
export type OracleReason = 'parse-exception' | 'mismatch';
export interface OracleAcceptResult { ok: boolean; reason?: OracleReason; detail?: string; }
export function acceptAgainstOracle(input: string, queryText: string): OracleAcceptResult;
```

Логика:

```
ours = generateBatch(parseBatch(input))   // ловим исключение → parse-exception
ok   ⇔ ours === queryText
mismatch.detail = первая расходящаяся строка (L<n>: <наше> ¦ <конструктор>)
```

CLI-обёртка читает `golden.jsonl`, гоняет `acceptAgainstOracle`, пишет
`tmp/query1c/oracle/report.json` + `summary.json`. Записи с `valid:false` на исходник
выносятся в корзину `oracle-invalid` (не наша вина, исключаются из знаменателя).

### 4.4. `test/fixtures/oracle/*.json` + `test/unit/oracleGolden.test.ts` — CI-регрессия

Курируемое подмножество в git: один файл = один кейс `{ name, input, expected }`, где
`expected` = `query_text` конструктора. По одному минимальному кейсу на класс конструкций
и **по кейсу на каждый исправленный в 6.8–6.11 баг**. Тест гоняет
`generateBatch(parseBatch(input))` и сравнивает с `expected` **без MCP**.

## 5. Форматы данных

`tmp/query1c/oracle/golden.jsonl` (gitignored, локальный) — по строке на запрос:

```json
{"file":"…bsl_1.txt","valid":true,"input":"ВЫБРАТЬ\n\t…","query_text":"ВЫБРАТЬ\n\tВалюты.Ссылка КАК Ссылка\n…"}
```

`tmp/query1c/oracle/summary.json`:

```
{ total, oracleInvalid, accepted, rejected,
  byReason: { "parse-exception": n, "mismatch": n },
  parseException: { topMessages: {msg: count} },
  mismatch: { topFirstDiffTokens: {token: count}, examples: [{file, detail}] } }
```

Группировка `mismatch` по характеру первой расходящейся строки (соединения / порядок /
псевдонимы / выражения) — чтобы 6.8+ брали корзины по убыванию частоты.

## 6. Критерии приёмки 6.7

- `golden.jsonl` собран по всему доступному корпусу (≈2088), резюмируемо.
- `oracleAccept` CLI отрабатывает корпус и выдаёт `report.json`/`summary.json` с
  бакетами `parse-exception` / `mismatch` / `accepted` / `oracle-invalid`.
- Юнит-тесты: `mcpClient.test.ts` (мок-fetch), `oracleAccept.test.ts` (синтетика всех
  четырёх исходов), `oracleGolden.test.ts` (курируемые фикстуры). Вся суита зелёная.
- MCP/сеть не задействованы при `npm run test:unit`.

## 7. Что НЕ входит в 6.7

Сами фиксы парсера/генератора — это 6.8 (верность модели), 6.9 (ИМЕЮЩИЕ), 6.10
(ВЫБОР/выражения), 6.11 (подзапросы в ИЗ, вложенные ОБЪЕДИНИТЬ). 6.7 — только мерило и
триаж: получить истинный список расхождений против конструктора.
