# Фаза 8.2. Семантическая валидация текста запроса (MCP 1c-md) — дизайн

← [Дорожная карта](../../ROADMAP.md) · [Фаза 8](../../PHASE_8.md)

Дата: 2026-06-23. Опирается на парсер Фаз 6–7 (`parseBatch`) и кэш метаданных Фазы 7.2.

## 1. Проблема

Сейчас критерий «открывается ли запрос конструктором» — **чисто синтаксический**:
`validateBatch.ts → tryParseBatch → parseBatch` (не бросил исключение → открываем).
Парсер не знает метаданных конфигурации, поэтому запрос на **несуществующую таблицу**
открывается как ни в чём не бывало. Эталонный пример из требований:

```
ВЫБРАТЬ
	Валюты.Ссылка КАК Ссылка,
	Валюты.Наименование КАК Наименование
ИЗ
	Справочник.Валюты1 КАК Валюты
		ЛЕВОЕ СОЕДИНЕНИЕ Справочник.БанковскиеСчета КАК БанковскиеСчета
		ПО Валюты.ОсновнаяВалюта = БанковскиеСчета.Ссылка
```

`Справочник.Валюты1` не существует (есть `Справочник.Валюты`) — такой текст **не должен
открываться**, но сегодня открывается.

## 2. Цель исследования

Прежде чем менять критерий открытия, нужно **эмпирически охарактеризовать** доступный
инструмент семантической проверки — MCP `1c-md.validate_query` — на большом наборе
вариантов (≥100), простых и сложных, чтобы понять:

1. ловит ли он несуществующие таблицы/поля и с какой точностью (позиция ошибки);
2. что он проверяет семантически, а что — нет (границы применимости);
3. годится ли он как «привратник» открытия конструктора и какие будут ложные срабатывания.

«Открывается» в терминах исследования == `validate_query` вернул `{valid:true}`;
«не открывается» == `{valid:false}` + текст ошибки.

## 3. Метод

6 параллельных субагентов, каждый — своя категория, каждый реально вызывает MCP
`validate_query` (и `list_metadata_objects`/`get_metadata_structure` для подбора реальных
имён объектов живой конфигурации `smallb`):

| # | Категория | Вариантов |
|---|-----------|-----------|
| A | Существование таблиц (все типы метаданных) | ≥22 |
| B | Поля, реквизиты, ТЧ, навигация через точку | ≥22 |
| C | Синтаксис и пограничные случаи (пусто/комментарий/`;`/англ.) | ≥22 |
| D | Виртуальные таблицы регистров (Остатки/Обороты/Срез…) | ≥22 |
| E | Сложные конструкции (ОБЪЕДИНЕНИЕ/ВТ/соединения/группировка/функции) | ≥26 |
| F | Реальный корпус `tmp/query1c/` + конфигураторная разметка `{…}` | ≥18 |

Итого ≥132 проверки. Результаты сводятся в отчёт
[`docs/phase8.2-validation-research.md`](../../phase8.2-validation-research.md).

## 4. Ключевые выводы (заполняется по итогам, см. отчёт)

`validate_query` — это **полноценный парсер платформы 1С с проверкой по метаданным**:
- ✅ ловит несуществующие таблицы («Таблица не найдена») и поля («Поле не найдено») с
  точной позицией `{(строка, столбец)}` и маркером `<<?>>`;
- ✅ проверяет навигацию через точку (только по ссылочным реквизитам), число колонок
  в ОБЪЕДИНЕНИИ, согласованность группировки, значения `ЗНАЧЕНИЕ(Перечисление.…)`,
  применимость виртуальной таблицы к типу регистра и состав её параметров;
- ⚠️ **не** проверяет: существование временных таблиц между пакетами, тип значений
  параметров `&П` и параметров ВТ, «голое» имя без точки (трактуется как ВТ/подзапрос);
- ⚠️ не поддерживает скалярный подзапрос `(ВЫБРАТЬ …)` в списке полей;
- ℹ️ регистронезависим (имена/ключевые слова), принимает английский синтаксис
  (`SELECT…FROM…AS`) и английские префиксы типов (`Catalog.`/`Document.`);
- ℹ️ при `valid:true` возвращает нормализованный `query_text` (канонизатор).

## 5. Рекомендация для реализации (отдельной подфазой)

Открытие конструктора и проверку при «ОК» гейтить **двухступенчато**:
1. `tryParseBatch` (как сейчас) — синтаксис, быстро, офлайн;
2. при доступном MCP — `validate_query`; `valid:false` → не открывать, показать
   `message` с позицией. Деградация: если MCP недоступен — прежнее поведение (только
   синтаксис), чтобы не блокировать офлайн-работу.

Учесть границы из §4: конфигураторную разметку `{…}` перед отправкой в `validate_query`
**вырезать НЕ нужно** — инструмент её понимает и нормализует (см. отчёт, категория F);
достаточно снять ведущие `|`. Кросс-пакетные ВТ по голому имени остаются на совести
синтаксиса. Реализация — за рамками этого исследования (только спецификация + отчёт).
