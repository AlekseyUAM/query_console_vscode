# Spec: Конфигурируемый механизм корпусного тестирования конструктора

**Дата:** 2026-06-13
**Цель:** Превратить ad-hoc набор скриптов (хардкод путей `tmp/...`) в полноценный,
сохранённый в git, конфигурируемый через `.env` механизм прогона конструктора
запросов против ПРОИЗВОЛЬНОЙ конфигурации 1С с генерацией структурированных
отчётов об ошибках.

## Сценарий пользователя (новая конфигурация)

1. Создаётся база с новой конфигурацией.
2. К базе подключается MCP-сервер `1c-md` (валидация запросов).
3. Из базы выгружаются «эталонные» запросы `ВЫБРАТЬ *` ко всем объектам метаданных
   (внешняя обработка 1С) → `META_QUERIES_DIR`.
4. Конфигурация выгружается в файлы → `CONFIG_DIR`.
5. Обновляется кэш метаданных конструктора (`npm run parse`) → `METADATA_CACHE_DIR`.
6. Из конфигурации извлекаются ВСЕ тексты запросов («ВЫБРАТЬ …»), валидируются через
   MCP; валидные сохраняются в `QUERY_CORPUS_DIR` + golden.
7. Каждый текст (config-извлечённые + meta-эталоны) проверяется конструктором.
8. Для каждого `parse-exception`/`mismatch` пишется JSON-файл в `ERRORS_DIR`.

## Конфигурация — `.env` в корне

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `META_QUERIES_DIR` | КаталогВыгрузкиЗапросовКМетаданным (эталоны `ВЫБРАТЬ *`) | `tmp/meta1c` |
| `CONFIG_DIR` | КаталогВыгрузкиКонфигурации (выгрузка в файлы) | `src/cf` |
| `METADATA_CACHE_DIR` | Кэш метаданных конструктора (YAML) | `tmp/parser_data` |
| `QUERY_CORPUS_DIR` | Корпус извлечённых запросов + `oracle/golden.jsonl` | `tmp/query1c` |
| `ERRORS_DIR` | КаталогОшибок (по одному JSON на ошибку) | `tmp/corpus-errors` |
| `MCP_URL` | URL MCP `1c-md`; пусто → берётся из `.mcp.json` | (пусто) |

- `.env` — в `.gitignore`; в git коммитится `.env.example`. Загрузчик работает и без
  `.env` (дефолты совпадают с текущим поведением → существующий gate сохраняется).
- Приоритет: дефолты < `.env` < `process.env`.

## Формат JSON-файла ошибки (`ERRORS_DIR/<file>.json`)

```json
{
  "файл": "<имя .txt в корпусе>",
  "причина": "mismatch | parse-exception",
  "исходныйТекстЗапроса": "<вход>",
  "текстВалидатора": "<query_text от MCP-оракула>",
  "текстКонструктора": "<вывод нашего конструктора, '' при parse-exception>",
  "классОшибки": "<имя класса исключения | 'mismatch'>",
  "номерСтроки": <1-based номер расходящейся строки | 0>
}
```

## Архитектура кода

- `src/cli/corpusConfig.ts` — единый загрузчик `.env` (без новых зависимостей) +
  резолв всех каталогов в абсолютные пути. `getConfig()`, `goldenPath(cfg)`.
- Рефактор (поведение при дефолтах НЕ меняется):
  `parseMetadata.ts`, `extractQueries.ts`, `harvestOracle.ts`, `oracleAcceptCli.ts`,
  `oracleDiff.ts` — читают пути из `corpusConfig`.
- `oracleAccept.ts` — `OracleAcceptResult` дополняется полями `ours`, `errorClass`,
  `errorLine` (аддитивно; `ok`/`reason` не меняются → числа приёмки те же).
- `oracleAcceptCli.ts` — на каждый провал пишет JSON в `ERRORS_DIR` (для чистого
  корпуса — 0 файлов; поведение summary не меняется). `ERRORS_DIR` очищается в начале.
- `src/cli/ingestMeta.ts` — копирует `META_QUERIES_DIR/*.txt` в `QUERY_CORPUS_DIR`
  с префиксом `meta__` (для прогона эталонов через ту же приёмку).
- `src/cli/corpusTest.ts` — оркестратор: parse → extract → ingest:meta → harvest →
  accept. Флаги `--skip-parse`, `--skip-harvest` для резюмирования.

## npm-скрипты

- существующие: `parse`, `harvest`, `accept:oracle`, `oracle:diff` — без смены поведения.
- новые: `extract`, `ingest:meta`, `corpus:test`.
