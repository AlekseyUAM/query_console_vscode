# Фаза 8.1. Сохранение комментариев запроса — дизайн

← [Дорожная карта](../../ROADMAP.md) · [Фаза 8](../../PHASE_8.md)

Дата: 2026-06-19. Опирается на парсер (Фаза 6, `parseBatch`) и генератор (`generateBatch`).

## 1. Проблема

В тексте запроса 1С бывают комментарии `//…`. Сейчас они **молча удаляются** при
открытии запроса конструктором (лексер `sdblLexer.ts:156-160` пропускает `//` до конца
строки, парсер `stripLineComments` вырезает их из «сырых» срезов). При сохранении из
конструктора текст пересобирается генератором — комментариев в нём уже нет, они теряются.

## 2. Цель (TO BE)

Сохранять комментарии **по умолчанию**. В шапке (рядом с кнопкой «Обновить кэш») —
галочка «Сохранять комментарии» (включена по умолчанию). Комментарии привязываются к
смысловым «якорям» модели и переживают цикл *открыть → править → сохранить*.

### Правила привязки (из требований)

Каждый комментарий принадлежит **контейнеру** — запросу пакета:
- если запрос создаёт временную таблицу (`ПОМЕСТИТЬ`), якорь — **имя ВТ**;
- иначе — **номер N пакета** (позиция в `BatchDocument.members`).

Удаление контейнера удаляет все его комментарии:
- удалить пакет N → его комментарии удаляются;
- удалить/переименовать ВТ → все комментарии этого запроса удаляются.

Внутри контейнера различаем 4 вида (всё прочее — **удаляется**):

| Вид | Где в тексте | Якорь | Удаляется при |
|----|--------------|-------|---------------|
| 1 | хвостом после поля: `Поле КАК Син, // c1` | синоним поля | удаление/переименование поля |
| 2 | отдельной строкой перед полем | синоним следующего поля | удаление/переименование поля |
| 3 | перед `ВЫБРАТЬ` (после авто-разделителя `////…`) | сам `ВЫБРАТЬ` | удаление/переименование контейнера |
| 4 | отдельной строкой после `ИЗ` (перед таблицей) | сам `ИЗ` | удаление/переименование контейнера |

Авто-разделитель пакетов `/'.repeat(80)` генерируется самим `generateBatch` (SEP) —
он **не** считается комментарием 3-го вида и при извлечении игнорируется.

## 3. Жёсткое ограничение совместимости

`generateBatch(parseBatch(input))` обязан остаться **байт-в-байт** для золотого оракула
(`oracleGolden.test.ts`) и регрессии корпуса 1976 запросов (`corpusRegression.test.ts`).
Значит сохранение комментариев — **opt-in** и **невидимо**, когда комментариев нет:

- `parseBatch` собирает комментарии только при явной опции `{ preserveComments: true }`;
  по умолчанию поведение не меняется (модель без полей комментариев).
- Генератор печатает комментарии **только если они есть в модели**; корпусные модели их
  не содержат → вывод неизменен.

## 4. Модель данных (`queryModel.ts`)

```ts
export interface QueryComments {
  beforeSelect?: string[]; // вид 3 — строки перед ВЫБРАТЬ (без авто-разделителя)
  afterFrom?: string[];    // вид 4 — строки после ИЗ, перед телом источника
}
// QueryModel.comments?: QueryComments
// SelectedField.commentLeading?: string[]; // вид 2 — строки перед полем
// SelectedField.commentTrailing?: string;  // вид 1 — хвост после поля (с «//»)
```

Комментарии видов 1/2 живут на `SelectedField` → автоматически переживают перенос поля и
исчезают при его удалении (поле выпадает из массива). Виды 3/4 живут на `QueryModel`.

Все строки хранятся **с префиксом `//`** (как в исходнике), без завершающего перевода
строки.

## 5. Лексер (`sdblLexer.ts`)

`tokenize(text, opts?: { comments?: boolean })`. По умолчанию `comments:false` —
поведение неизменно (комментарии пропускаются). При `comments:true` на `//…` эмитится
токен `{ type: 'comment', value, text, pos, line, col }` (новый тип в `TokenType`). Текст
токена — от `//` до конца строки (без `\n`).

Парсер `Cursor` использует `tokenize` без опции → его поток токенов не меняется.

## 6. Связыватель комментариев (`commentBinder.ts`, новый)

`extractComments(memberText: string, model: QueryModel): void` — мутирует модель,
проставляя `comments`/`commentLeading`/`commentTrailing`. Никогда не бросает (всё в
try/catch у вызывающего; внутренние ошибки → комментарии просто не привязаны).

Алгоритм: `tokenize(memberText, {comments:true})`, найти на верхнем уровне (глубина
скобок 0) первый `ВЫБРАТЬ` и первый `ИЗ`; список полей — токены между `ВЫБРАТЬ` и
(`ПОМЕСТИТЬ`/`ДОБАВИТЬ`/`ИЗ`/конец), порезанные по запятым верхнего уровня = сегменты-поля.
Для каждого комментария:
- до `ВЫБРАТЬ` → вид 3 (`beforeSelect`), строки из одних `/` (авто-разделитель) пропускаются;
- в списке полей: на одной строке с содержимым сегмента → вид 1 (`commentTrailing` поля);
  отдельной строкой → вид 2 (`commentLeading` **следующего** поля);
- после `ИЗ` до первого токена источника, отдельной строкой → вид 4 (`afterFrom`);
- иначе → отбрасывается.

Сегмент → поле модели: по синониму (`КАК <ident>` сегмента ↔ `fieldAlias(field, model)`),
с откатом на позиционное соответствие. Если у вида 2 нет следующего поля — отбрасывается.

**ОБЪЕДИНЕНИЕ:** для пакета-ОБЪЕДИНЕНИЯ текст режется на участников `splitUnionMemberTexts`
(инверсия `splitUnionMembers`: границы — `ОБЪЕДИНИТЬ [ВСЕ]` верхнего уровня; срез участника
содержит ведущие комментарии перед его `ВЫБРАТЬ`), и связыватель вызывается на каждом
участнике → комментарии привязаны к QueryModel участника = к его **номеру** в объединении.

## 7. Парсер (`sdblParser.ts`)

`parseBatch(text, resolver?, opts?: { preserveComments?: boolean })` и
`parseDocument(text, resolver?, opts?)` — новый необязательный параметр. При
`preserveComments` после сборки модели каждого чанка с **одним** участником вызывается
`extractComments(chunk, doc.members[0].model)` в try/catch. Существующие 2-арг вызовы не
затрагиваются.

## 8. Генератор (`sdblGenerator.ts`)

В `buildQueryBlock`:
- `model.comments?.beforeSelect` — строки **в начало** блока (col 0), перед `ВЫБРАТЬ`;
- `model.comments?.afterFrom` — между `'ИЗ'` и телом `renderFrom` (col 0);
- для каждого поля: `commentLeading` — отдельными строками (col 0) перед строкой поля;
  `commentTrailing` — **после** запятой в хвост строки поля (` ` + текст).

Вид 1 печатается там, где навешиваются запятые (массив `lines` в `buildQueryBlock`,
строка ~1606). Если у поля нет полей-комментариев — вывод не меняется → корпус цел.

## 9. Состояние webview (`queryStore.ts`)

- `SavedQuery.comments?: QueryComments`; `QueryState.queryComments?: QueryComments`.
- Протянуть через `snapshotActive`/`restoreSaved`/`buildModelFromFlat`/`modelToFlat`/
  `docToSnapshot`/`assembleBatch`. Поля-комментарии едут на `selectedFields` сами.
- Сброс по правилам:
  - `SET_TEMP_TABLE_NAME` (переименование ВТ-контейнера) → очистить `queryComments` и
    `commentLeading/commentTrailing` всех полей;
  - `SET_QUERY_TYPE` (смена типа запроса = смена контейнера) → то же;
  - `SET_COLUMN_ALIAS` / `SET_FIELD_EXPRESSION` (переименование поля) → очистить
    комментарии затронутого поля;
  - `REMOVE_FIELD` → поле выпадает с комментариями (уже работает);
  - `REMOVE_BATCH_QUERY`/`REMOVE_QUERY` → снимок удаляется с комментариями (уже работает).

## 10. UI и поток (`App.tsx`, `validateBatch.ts`)

- `tryParseBatch(text, opts?)` → проброс в `parseBatch`. `validateBatchText` — без опций
  (валидации комментарии не нужны; генерируемый текст с комментариями обязан парситься).
- В `App.tsx`: `const [preserveComments, setPreserveComments] = useState(true)`. Чекбокс в
  `cacheToolbar`. Загрузка: `tryParseBatch(msg.text, { preserveComments: true })`.
  Текст для вставки: `generateBatch(preserveComments ? batch : stripComments(batch))`, где
  `batch = assembleBatch(state)`, `stripComments` — хелпер, снимающий поля комментариев.
- Протокол сообщений и `panel.ts`/`insertResult.ts` **не меняются**: комментарии уже
  внутри `batchText` (BSL-обёртка `formatAsBslString` навешивает `|` на все строки, включая
  строки-комментарии — это валидный текст запроса внутри строкового литерала).

## 11. Тесты (TDD)

- `sdblLexer` — эмиссия comment-токенов при `{comments:true}`, неизменность по умолчанию.
- `commentBinder` — 4 вида + отбрасывание прочих + игнор авто-разделителя.
- `sdblGenerator` — печать каждого вида; отсутствие комментариев → прежний вывод.
- **Приёмка**: `generateBatch(parseBatch(SPEC_EXAMPLE, undefined, {preserveComments:true}))`
  === ожидаемый канонический текст (пример из требований).
- `queryStore` — сброс комментариев по правилам 9.
- Регрессия: `oracleGolden`/`corpusRegression` — без изменений (зелёные).
