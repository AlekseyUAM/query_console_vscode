## Контекст и цель

Фаза 7 довела до конца жест «открыть существующий запрос в нашем конструкторе». Но
**правильность открытия** (что панели Таблицы/Поля/Условия и т.д. заполнены так же, как
их показал бы настоящий конструктор 1С) пока проверяется только глазами. Прежде чем
автоматизировать такую проверку на корпусе (это отдельная **Подфаза 7.4**), нужно:

1. **Доказать выполнимость** управления реальным конструктором 1С из этого окружения
   через Playwright.
2. **Собрать визуальный референс** настоящего конструктора и **опись его UI** —
   вход для задач на доработку нашего webview.

Реальная веб-публикация базы доступна из devcontainer: `http://host.docker.internal/smallb/ru_RU/`
→ HTTP 200, веб-клиент 1С (маркеры `E1CIB`). `localhost` из контейнера НЕ работает —
только `host.docker.internal` (хост виден как `172.17.0.1`).

### Что НЕ входит в эту подфазу (YAGNI / граница с 7.4)

- Скрап структуры DOM веб-клиента (хрупко; договорились «обойдёмся скриншотами»).
- Пиксель-/layout-дифф.
- Любое сравнение с нашим конструктором и прогон по корпусу (17933) — это **Подфаза
  7.4**, оракул которой = реальный конструктор; механизм подачи запросов и сопоставления
  результата проектируется отдельным спеком.

## Архитектура

Артефакт — **tooling** (как корпусный харнесс), не unit/e2e нашего webview: pure-TS
модуль + bundled-CLI входы (`esbuild → node`), браузер через `chromium.launch()` из
уже установленного `@playwright/test`.

Каталог `tooling/real-constructor/`:

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `config.ts` | Конфиг из `.env` (приоритет дефолты < `.env` < `process.env`), по образцу `src/cli/corpusConfig.ts`. Ключи: `WEB_1C_URL`, `USER_1C`, `PASSWORD_1C`. | `fs`, `path` |
| `session.ts` | `launch()` → headless chromium, viewport 1600×1000; `login(page)`: навигация на `WEB_1C_URL`, заполнение формы аутентификации, ожидание рабочего стола. | playwright, `config` |
| `console.ts` | `openQueryConsole(page)`: переход по навигационной ссылке, ожидание формы обработки. | playwright |
| `constructor.ts` | `loadQueryIntoConstructor(page, text)`: вставить текст, открыть «Конструктор запроса», дождаться модального диалога. `walkTabs(page, shotDir)`: обойти вкладки, рекурсивно открыть под-окна, скриншотить. | playwright, `screenshot` |
| `screenshot.ts` | Сохранение PNG с предсказуемыми именами `<NN>-<вкладка>.png`. | playwright, `fs` |

CLI-входы (через `npm run`, `esbuild → node`):
- `real:setup` — подсказка/обёртка `npx playwright install chromium` (+ `install-deps`).
- `real:smoke` — 1 эталонный запрос, скриншоты всех вкладок.
- `real:inventory` — 10 сложных запросов, полный рекурсивный обход.

Конфиг расширяет подход `corpusConfig.ts`. Новые дефолты:
`WEB_1C_URL = http://host.docker.internal/smallb/ru_RU/`. `USER_1C`/`PASSWORD_1C` уже в `.env`
(`Администратор` / пустой пароль).

## Поток драйвера

```
launch chromium (headless, viewport 1600×1000)
  → login: goto WEB_1C_URL → fill user/password (локаторы по роли/подписи) → submit → wait рабочий стол
  → openQueryConsole: goto  WEB_1C_URL + "#e1cib/app/Обработка.КонсольЗапросов" → wait форма
  → loadQueryIntoConstructor: вставить текст в поле запроса → нажать «Конструктор запроса» → wait модальный диалог
  → walkTabs: для каждой вкладки [Таблицы и поля, Связи, Группировка, Условия,
       Дополнительно, Объединения/Псевдонимы, Порядок, Итоги, …]
         click вкладку → screenshot → найти кнопки, открывающие под-окна →
         для каждого: open → screenshot → recurse (depth, seen) → close
  → закрыть диалог, браузер
```

### Навигационная ссылка

Обработка открывается прямой навигационной ссылкой 1С (меню не трогаем):

```
WEB_1C_URL + "#e1cib/app/Обработка.КонсольЗапросов"
```

Если прямой переход не сработает — резолвить ссылку через MCP `get_nav_link` (в проекте
доступен) как запасной путь.

### Рисковые шаги и страховка

1. **Форма логина** — селекторы полей заранее неизвестны: локаторы по роли/видимой
   подписи (`getByRole('textbox')`, и т.п.), не по сгенерированным id. Smoke проверяет
   это первым.
2. **Достучаться до «Консоли запросов»** — снято заданной навигационной ссылкой
   `e1cib/app/Обработка.КонсольЗапросов`.
3. **Рекурсия по под-окнам** — обход с ограничением **глубины (по умолчанию 3)** и
   множеством «уже виденных» заголовков окон против зацикливания.

**Принцип устойчивости:** драйвер НЕ падает на отдельном непонятном элементе — он
скриншотит, пишет в `tmp/real-constructor.log` и идёт дальше. Цель smoke — собрать
максимум, а не пройти зелёным тестом. Тайминги — явные `waitFor` с запасом (веб-клиент
1С грузится небыстро).

## Верификация

Это tooling, не pass/fail-тест.

- **smoke сам — приёмка выполнимости:** залогинился → открыл «Консоль запросов» →
  загрузил эталонный запрос в конструктор → сохранил скриншоты всех вкладок ⇒ доказано.
- **Юнит-тесты (vitest)** — только pure-логика без браузера:
  - парсинг конфига (`WEB_1C_URL`/креды, приоритет дефолты < `.env` < `process.env`);
  - **страж рекурсии** (ограничение глубины + дедуп виденных окон).
  Драйвер браузера юнитами не покрываем — его «тест» это smoke.

## Связь с Подфазой 7.4

Примитивы `session`/`console`/`constructor` строятся начисто здесь, потому что
корпусной прогон 7.4 (оракул = реальный конструктор) переиспользует ровно их: логин,
открытие «Консоли запросов», загрузка текста в конструктор, скриншот. Открытая
проблема 7.4 (как подавать 17933 запроса и как сопоставлять результат, раз сверять
17933 пар скриншотов руками/пиксельно нереально) решается её собственным спеком.
