# Фаза 4.5 — Тестирование текстов запросов

Дата: 2026-06-07 · Статус: дизайн утверждён, готов к плану.

См. также: [ROADMAP](../../ROADMAP.md) · предыдущие фазы 4.1–4.4.

## Проблема

Фазы 4.1–4.4 закрыли парсер 17 типов метаданных и генерацию SDBL для реальных и
виртуальных таблиц регистров (сведений, накопления, бухгалтерии) с зависимостью полей
от вида ВТ и периодичности. Покрытие тестами — точечное, по отдельным хелперам
(`accumVirtualFields`, `accountingVirtualTables`). Нет сквозной проверки, что весь
конвейер «YAML → модель метаданных → выбор всех полей → генератор SDBL» воспроизводит
текст запроса, который выдаёт штатный «Конструктор запроса» 1С.

В каталоге `tmp/meta1c/` лежат 520 эталонных текстов запросов, выгруженных из 1С штатным
конструктором, по одному на сочетание объект × виртуальная таблица × периодичность. Это
золотой стандарт: имена полей, их порядок, состав полей ВТ по периодичности, синтаксис
источника. Имена файлов: `[ИмяТипа][ИмяМетаданного][ИмяВиртуальнойТаблицы][Периодичность].txt`.

Отдельная задача — **общие реквизиты** (`ОбщиеРеквизиты`): у каждого есть состав
(`Состав`), поэтому общий реквизит становится полем многих объектов. В эталонах это
видно: `НаименованиеЯзык1/2` встречаются в 9 файлах, `ОбластьДанных*` — в 16,
`ОтредактированныеПредопределенныеРеквизиты` — в 14. Генератор обязан добавлять поля
общих реквизитов в объекты их состава.

## Цель

Сквозное доказательство, что конвейер метаданные → генератор воспроизводит вывод штатного
конструктора 1С, с `validate_query` (MCP `1c-md`) как независимым оракулом валидности.

## Артефакты

1. **Хелпер `buildSelectAllModel`** — по таблице метаданных (+ опционально вид ВТ и
   периодичность) строит `QueryModel`, выбирающий все поля в порядке 1С:
   стандартные реквизиты → собственные реквизиты → **поля общих реквизитов из состава** →
   табличные части → хвостовые стандартные (`Предопределенный`, `ИмяПредопределенныхДанных`).
   Опирается на существующие билдеры ВТ (`accumVirtualFields`, `accountingVirtualTables`,
   срезы РС). Это единица, кодирующая «все поля X»; именно её прогоняет golden-тест.
   Точный порядок полей выводится из анализа эталонов.

2. **Golden-сьют `test/unit/sdblGolden.test.ts`** — грузит
   `tmp/parser_data/cf/configuration.yaml`, и для ~40–60 репрезентативных эталонов
   (каждый вид таблицы × каждая ВТ × каждая периодичность × ТЧ × общие реквизиты ×
   ссылочные поля) проверяет `expect(generate(buildSelectAllModel(...))).toBe(<эталон без BOM>)`.
   Репрезентативность по функциям (решение пользователя), а не по всем 520 файлам.

3. **Матрица валидации `docs/superpowers/specs/2026-06-07-phase4.5-validation-matrix.md`** —
   результаты прогона `validate_query` по эталонному корпусу: valid/invalid по каждому
   функциональному кейсу. Доказывает, что golden-эталоны — настоящий SDBL 1С.

## Поток данных golden-теста

```
configuration.yaml ──loadYaml──▶ MetaTable[]
                                     │ (+ слияние общих реквизитов по составу)
                                     ▼
            выбранный объект ──buildSelectAllModel(obj, vt?, period?)──▶ QueryModel
                                     │
                                     ▼
                               generate(model) ──toBe──▶ tmp/meta1c/<...>.txt (без BOM)
```

## Репрезентативные функциональные классы (что обязательно покрыть)

- **Справочник** — стандартные реквизиты, собственные, ТЧ (раскрытие подполей),
  хвостовые стандартные (`Предопределенный`, `ИмяПредопределенныхДанных`).
- **Документ** — стандартные (`Номер`, `Дата`, `Проведен`), собственные, ТЧ.
- **Перечисление** — `Ссылка`, `Порядок`, представления (минимальный кейс).
- **Общие реквизиты** — объект из состава общего реквизита получает его поля
  (`НаименованиеЯзык1/2`, `ОбластьДанных*`, `ОтредактированныеПредопределенныеРеквизиты`).
- **Регистр сведений** — реальная таблица; `СрезПервых`/`СрезПоследних` (периодический);
  отсутствие срезов у непериодического (нет файла-эталона).
- **Регистр накопления** — реальная таблица; `Остатки`/`Обороты`/`ОстаткиИОбороты`;
  зависимость полей `Обороты`/`ОстаткиИОбороты` от периодичности
  (Период/Запись/Регистратор/Секунда…Полугодие/Год/Авто).
- **Регистр бухгалтерии** — реальная таблица; `Остатки`/`Обороты`/`ОстаткиИОбороты`/
  `ДвиженияССубконто`; `ОборотыДтКт` для корреспондентских; развёртка
  счетов/субконто/ресурсов; зависимость от периодичности.
- **Прочие типы из эталонов** — план видов характеристик/счетов/расчёта, бизнес-процесс,
  задача — по одному кейсу, если присутствуют в `tmp/meta1c`.

## Обработка ошибок и расхождений

- BOM (`﻿`) в эталонах снимается перед сравнением.
- Если golden-тест вскрывает реальный разрыв (общие реквизиты не попадают в поля,
  порядок/имена полей расходятся с 1С) — **исправляется в рамках фазы 4** в `src/core`,
  пока тест не станет зелёным (решение пользователя). Это входит в условие закрытия фазы 4.
- Непериодические регистры срезов/ВТ не имеют — для них golden-тест проверяет отсутствие
  соответствующего эталонного файла, а не пустой вывод.

## Тестирование

- Golden-сьют (vitest) — регрессия в CI.
- `validate_query` — внешний оракул, прогоняется автором по эталонам, результат — в матрице
  валидации (не в CI, т.к. MCP-инструмент недоступен из vitest).

## Что не входит

- Покрытие всех 520 файлов по отдельности (выбрана репрезентативность по функциям).
- Обратный разбор текста (фаза 6).
- Разворот небалансовых измерений в Дт/Кт, параметры-субконто в окне (вне фазы 4.4).
