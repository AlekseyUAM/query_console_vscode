# Корпусное тестирование конструктора запросов

Как прогнать конструктор запросов против другой конфигурации 1С: выгрузить из базы
эталонные запросы и тексты из кода, провалидировать их через MCP-оракул `1c-md`,
прогнать через конструктор и получить по одному JSON-файлу на каждое расхождение.

Механизм конфигурируется через `.env` (см. Шаг 0); без `.env` работают значения по
умолчанию, совпадающие с поведением репозитория.

## Предусловия

- База 1С с тестируемой конфигурацией.
- MCP-оракул `1c-md` поднят как HTTP-сервис этой базы (см. ниже); параметры
  подключения — в `.mcp.json`.
- Node.js ≥ 20 и установленные зависимости: `npm install`.

### Развёртывание MCP-оракула `1c-md`

Оракул — это HTTP-сервис, который отдаёт расширение
[`tooling/mcp_tools/mcp_tools.cfe`](../tooling/mcp_tools/mcp_tools.cfe). Чтобы он
заработал на тестируемой базе:

1. **Загрузить расширение в базу.** Конфигуратор → **Конфигурация → Расширения
   конфигурации**, добавить расширение и через **Загрузить конфигурацию из файла…**
   указать `tooling/mcp_tools/mcp_tools.cfe`. Обновить конфигурацию базы данных
   (`F7`). Расширение добавляет HTTP-сервис с MCP-инструментами (`validate_query`,
   `execute_query`, метаданные и т. п.).
2. **Опубликовать базу на веб-сервере.** Конфигуратор → **Администрирование →
   Публикация на веб-сервере…**, включить публикацию HTTP-сервисов и опубликовать
   базу (например, под именем `sslplus`). После публикации HTTP-сервис MCP доступен
   по адресу вида `http://<хост>/<имя_публикации>/hs/mcp/`.
3. **Прописать `1c-md` в `.mcp.json`** (в корне репозитория) — указать URL
   опубликованного HTTP-сервиса:

   ```json
   {
     "mcpServers": {
       "1c-md": {
         "type": "http",
         "url": "http://host.docker.internal/sslplus/hs/mcp/"
       }
     }
   }
   ```

   `host.docker.internal` — хост, на котором опубликована база (так dev-контейнер
   достучится до веб-сервера на хост-машине); `sslplus` — имя публикации. Подставьте
   свои хост и имя публикации. Этот же URL можно переопределить через `MCP_URL` в
   `.env` (см. Шаг 0).

## Шаг 0. Настройка `.env`

Скопируйте шаблон и при необходимости поправьте значения:

```bash
cp .env.example .env
```

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `META_QUERIES_DIR` | Каталог эталонных запросов `ВЫБРАТЬ *` к метаданным (выгрузка внешней обработки 1С) | `tmp/meta1c` |
| `CONFIG_DIR` | Каталог выгрузки конфигурации 1С в файлы | `src/cf` |
| `METADATA_CACHE_DIR` | Кэш метаданных конструктора (YAML), генерируется `npm run parse` | `tmp/parser_data` |
| `QUERY_CORPUS_DIR` | Корпус извлечённых запросов + эталон оракула `oracle/golden.jsonl` | `tmp/query1c` |
| `ERRORS_DIR` | Каталог отчётов об ошибках приёмки (по одному JSON на ошибку) | `tmp/corpus-errors` |
| `MCP_URL` | URL MCP-сервера `1c-md`; пусто → берётся из `.mcp.json` | (пусто) |

Приоритет значений: дефолты < `.env` < переменные окружения (`process.env`). Без
файла `.env` всё работает на дефолтах — существующий gate (1976/1976) сохраняется.

## Шаг 1. Выгрузка эталонных запросов к метаданным

Запустите внешнюю обработку из [`tooling/1c-export/`](../tooling/1c-export/README.md)
на базе с тестируемой конфигурацией. Она обходит все метаданные, формирует
`ВЫБРАТЬ * ИЗ <Тип>.<Объект>` (и запросы к виртуальным таблицам регистров с разными
периодичностями), валидирует их через `СхемаЗапроса` и сохраняет нормализованный
текст в файлы.

Результат — `*.txt` по одному запросу на файл в каталоге `META_QUERIES_DIR`. Каталог
выгрузки задаётся в самой обработке и должен совпадать с `META_QUERIES_DIR`.

## Шаг 2. Выгрузка конфигурации в файлы

В Конфигураторе: **Конфигурация → Выгрузить конфигурацию в файлы** в каталог
`CONFIG_DIR`. На выходе — `*.xml` (метаданные) и `*.bsl` (код модулей).

## Шаг 3. Обновление кэша метаданных конструктора

```bash
npm run parse
```

Парсит выгрузку из `CONFIG_DIR` в YAML-кэш `METADATA_CACHE_DIR` (полная
перегенерация). На этом кэше конструктор строит дерево «таблицы → поля → типы».

## Шаг 4. Извлечение и валидация запросов из конфигурации

```bash
npm run extract       # скан *.bsl в CONFIG_DIR, поиск текстов «ВЫБРАТЬ …» → QUERY_CORPUS_DIR
npm run ingest:meta   # подмешать эталоны из META_QUERIES_DIR (префикс meta__) в корпус
npm run harvest       # валидация запросов через MCP-оракул → oracle/golden.jsonl
```

- `extract` собирает запросы из двух источников и складывает их в
  `QUERY_CORPUS_DIR` — по одному `*.txt` на запрос (имя файла кодирует путь
  источника и порядковый номер). Текст-дубликаты отбрасываются: один и тот же
  запрос, встреченный в нескольких местах (хоть в `.bsl`, хоть в XML),
  сохраняется один раз.
  - **BSL-модули** — сканирует все `*.bsl` в `CONFIG_DIR`, разбирает строковые
    литералы в двойных кавычках (с учётом экранирования `""`, склейки
    строк-продолжений по `|` и пропуска комментариев `//` и литералов-дат `'…'`)
    и оставляет те, что начинаются с `ВЫБРАТЬ` или `УНИЧТОЖИТЬ`.
  - **XML-макеты СКД** — обходит только поддерево `Reports/` (`Reports/**/*.xml`,
    например `Reports/Задачи/Templates/ОсновнаяСхемаКомпоновкиДанных/Ext/Template.xml`)
    и вытаскивает тело каждого элемента `<query>…</query>`. В XML спецсимволы
    запроса хранятся как сущности, поэтому тело декодируется: именованные
    `&amp;`/`&lt;`/`&gt;`/`&quot;`/`&apos;` и числовые `&#nn;`/`&#xHH;`.
    Декодирование идёт одним проходом слева направо, чтобы двойное экранирование
    `&amp;lt;` дало литерал `&lt;`, а не `<`. Тело берётся дословно (без `trim`) и
    фильтруется по тому же критерию `ВЫБРАТЬ`/`УНИЧТОЖИТЬ` — на выходе текст
    совпадает с тем, как тот же запрос выглядел бы в `.bsl`.
- `ingest:meta` копирует `META_QUERIES_DIR/*.txt` в `QUERY_CORPUS_DIR` с префиксом
  `meta__`, чтобы эталоны прошли через ту же приёмку.
- `harvest` отправляет каждый запрос в MCP-оракул `1c-md`; валидные запросы с их
  нормализованным текстом (`query_text` оракула) пишутся в `oracle/golden.jsonl`,
  невалидные отбрасываются. Подкаталог `oracle/` создаётся скриптом относительно
  `QUERY_CORPUS_DIR` (`<QUERY_CORPUS_DIR>/oracle/golden.jsonl`; по умолчанию
  `tmp/query1c/oracle/golden.jsonl`) — вручную создавать не нужно. Имя `oracle`
  фиксировано в коде; через `.env` настраивается только родитель
  `QUERY_CORPUS_DIR`.

## Шаг 5. Приёмка

```bash
npm run accept:oracle
```

Прогоняет каждый запрос из golden через конструктор и сравнивает его вывод с текстом
оракула. Пишет сводку (`report.json` / `summary.json`) и по одному JSON-файлу на
каждую ошибку в `ERRORS_DIR` (каталог очищается в начале прогона; на чистом корпусе
— 0 файлов).

## Шаг 6. Одной командой

```bash
npm run corpus:test
```

Запускает весь конвейер: `parse → extract → ingest:meta → harvest → accept`.
Флаги для резюмирования:

- `--skip-parse` — пропустить пересборку кэша метаданных (Шаг 3);
- `--skip-harvest` — пропустить повторную валидацию через оракул (использовать
  существующий `oracle/golden.jsonl`).

## Формат файла ошибки

На каждую ошибку приёмки создаётся файл `ERRORS_DIR/<имяфайла>.json`:

| Поле | Значение |
|---|---|
| `файл` | Имя `.txt`-файла в корпусе |
| `причина` | `mismatch` или `parse-exception` |
| `исходныйТекстЗапроса` | Входной текст запроса |
| `текстВалидатора` | `query_text` от MCP-оракула (эталон) |
| `текстКонструктора` | Вывод нашего конструктора (`''` при `parse-exception`) |
| `классОшибки` | Имя класса исключения либо `mismatch` |
| `номерСтроки` | 1-based номер расходящейся строки либо `0` |

Пример:

```json
{
  "файл": "РегистрНакопления_Продажи_Обороты_Месяц.txt",
  "причина": "mismatch",
  "исходныйТекстЗапроса": "ВЫБРАТЬ * ИЗ РегистрНакопления.Продажи.Обороты(, , Месяц)",
  "текстВалидатора": "ВЫБРАТЬ\n\t...\nИЗ\n\tРегистрНакопления.Продажи.Обороты(, , Месяц)",
  "текстКонструктора": "ВЫБРАТЬ\n\t...\nИЗ\n\tРегистрНакопления.Продажи.Обороты(, , Месяц)",
  "классОшибки": "mismatch",
  "номерСтроки": 5
}
```

## Разбор ошибок

Каждый JSON в `ERRORS_DIR` самодостаточен: в нём есть исходный текст, эталон
оракула, вывод конструктора, класс ошибки и номер расходящейся строки. По этим
файлам заводятся точечные правки конструктора — отдельный файл на отдельный класс
расхождения, без необходимости заново гонять весь конвейер.

## Замечание про gate

На исходной конфигурации репозитория `npm run accept:oracle` даёт **1976/1976**
(0 расхождений). Команда `corpus:test` **перезаписывает** `oracle/golden.jsonl`,
поэтому запускать её на «боевой» (другой) конфигурации следует только осознанно: для
проверки текущего gate используйте `accept:oracle` (или `corpus:test --skip-harvest`
с уже собранным golden).

## Закоммиченный эталон (регресс-тест в `npm run test:unit`)

Рабочие каталоги (`tmp/query1c`, `tmp/parser_data`) — в `.gitignore`, поэтому на
свежем checkout'е воспроизвести gate через `accept:oracle` нельзя. Чтобы корпус из
1976 запросов был частью обычного прогона тестов, его эталон закоммичен в
`test/fixtures/corpus/`:

- `golden.jsonl` — `{file, valid, input, query_text}` по каждому запросу;
- `metadata/cf/` — YAML-кэш метаданных для развёртки `ВЫБРАТЬ *` (нужен 27 запросам).

Тест `test/unit/corpusRegression.test.ts` прогоняет весь корпус
(`generateBatch(parseBatch(input, resolver)) === query_text`) и падает при любом
расхождении. Он не зависит ни от `tmp/`, ни от MCP — поэтому
**`npm run test:unit` воспроизводит gate 1976/1976 на любом checkout'е**.

### `npm run corpus:snapshot` — обновление эталона (осознанно!)

```bash
npm run corpus:snapshot   # tmp/query1c/oracle/golden.jsonl + tmp/parser_data/cf → test/fixtures/corpus
```

Эта команда **переопределяет закоммиченный gate** тем, что сейчас лежит в `tmp`: она
копирует живой `golden.jsonl` и YAML-кэш метаданных в `test/fixtures/corpus`. Это
единственный способ изменить эталон в git — поэтому запускать её нужно осознанно,
понимая, *какая* конфигурация и *какое* состояние конструктора станут новым gate.

**Когда запускать:**

- Ты **намеренно улучшил конструктор** (парсер/генератор) на текущей конфигурации,
  живой `npm run accept:oracle` снова даёт 1976/1976 с новым корректным выводом —
  snapshot переносит свежий эталон в gate (вместо ручного копирования файлов).
- Ты **осознанно решил сделать другую конфигурацию закоммиченным эталоном**: прогнал
  её по конвейеру, привёл к 0 расхождений и хочешь, чтобы регресс-gate был по ней.

**Когда НЕ запускать:**

- Во время **поиска багов на новой конфигурации.** У неё заведомо есть mismatch /
  parse-exception (конструктор настраивался на исходной). `corpus:snapshot` тогда
  **зашьёт эти ошибки в эталон** — gate перестанет ловить регрессии. Пока чинишь
  конструктор, gate'ом остаётся исходный 1976 (он проверяет, что починка ничего не
  сломала на известно-правильной конфигурации), а ошибки новой конфигурации живут в
  `ERRORS_DIR` и разбираются отдельно.

**Замечание про `sdblGolden`.** `corpus:snapshot` обновляет только корпус reverse-parse
(`golden.jsonl` + `metadata/cf`). Эталоны select-all теста `sdblGolden.test.ts`
(`test/fixtures/corpus/meta1c`, фиксированное подмножество объектов под захардкоженные
имена) snapshot НЕ трогает — при смене конфигурации этот тест и его эталоны
обновляются отдельно (или тест перенацеливается на объекты новой конфигурации).
