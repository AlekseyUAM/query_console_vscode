## Подфаза 1. Сохранение комментариев запроса — ✅ закрыто (2026-06-19)

Спек: [`2026-06-19-phase8.1-comments-design.md`](superpowers/specs/2026-06-19-phase8.1-comments-design.md) ·
план: [`2026-06-19-phase8.1-comments.md`](superpowers/plans/2026-06-19-phase8.1-comments.md).

**Что было не так.** Комментарии `//…` в тексте запроса молча терялись: лексер пропускал
`//` до конца строки, парсер вырезал их из «сырых» срезов (`stripLineComments`). При
сохранении из конструктора текст пересобирался генератором уже без комментариев.

**Итог.** Комментарии сохраняются **по умолчанию**. В шапке (рядом с кнопкой «Обновить
кэш») — галочка «Сохранять комментарии», включена по умолчанию. Комментарии привязываются
к смысловым якорям модели и переживают цикл *открыть → править → сохранить*.

### Правила привязки

Контейнер комментария — запрос пакета: имя ВТ (если запрос `ПОМЕСТИТЬ`), иначе номер N
пакета. Удаление контейнера удаляет его комментарии; переименование/смена типа ВТ — тоже.
Внутри контейнера — 4 вида (всё прочее отбрасывается):

| Вид | Где | Якорь | Удаляется при |
|----|-----|-------|---------------|
| 1 | хвост после поля `Поле КАК Син, // c1` | синоним поля | удаление/переименование поля |
| 2 | отдельной строкой перед полем | синоним следующего поля | удаление/переименование поля |
| 3 | перед `ВЫБРАТЬ` (после авто-разделителя) | `ВЫБРАТЬ` | удаление/переименование контейнера |
| 4 | отдельной строкой после `ИЗ` | `ИЗ` | удаление/переименование контейнера |

Авто-разделитель пакетов `////…` (80 слэшей) генерируется самим `generateBatch` и не
считается комментарием 3-го вида (при извлечении игнорируется).

### Архитектура (где что лежит)

- **Модель** (`queryModel.ts`): `QueryComments { beforeSelect?; afterFrom? }` на
  `QueryModel.comments`; `SelectedField.commentLeading?: string[]` (вид 2) и
  `commentTrailing?: string` (вид 1). Комментарии полей едут на самих полях →
  автоматически переживают перенос и исчезают при удалении поля.
- **Лексер** (`sdblLexer.ts`): тип токена `'comment'`; `tokenize(text, { comments:true })`
  эмитит токены комментариев. По умолчанию — прежнее поведение (комментарии пропускаются).
- **Связыватель** (`commentBinder.ts`, новый): `extractComments(memberText, model)` —
  токенизирует с комментариями, классифицирует по видам 1–4 и мутирует модель. Никогда не
  бросает.
- **Парсер** (`sdblParser.ts`): `parseBatch`/`parseDocument` принимают
  `opts?: ParseOptions { preserveComments? }`; при включении после разбора вызывают
  связыватель на тексте каждого оператора (try/catch). Для **ОБЪЕДИНЕНИЯ** текст режется
  на участников (`splitUnionMemberTexts`, инверсия `splitUnionMembers`), и комментарии
  привязываются к QueryModel каждого участника — т. е. к его **номеру** в объединении.
  По умолчанию — без изменений.
- **Генератор** (`sdblGenerator.ts`): `buildQueryBlock` печатает комментарии из модели
  (beforeSelect перед `ВЫБРАТЬ`; afterFrom между `ИЗ` и телом; leading — отдельными
  строками перед полем; trailing — в хвост строки поля после запятой). Только при наличии
  данных → канонический вывод без комментариев не меняется.
- **Состояние webview** (`queryStore.ts`): `comments` протянут через
  snapshot/restore/model-конвертеры/`assembleBatch`; сброс по правилам в reducer
  (`SET_TEMP_TABLE_NAME`, `SET_QUERY_TYPE`, `SET_COLUMN_ALIAS`, `SET_FIELD_EXPRESSION`);
  хелпер `stripBatchComments` для генерации при снятой галочке.
- **UI/поток** (`App.tsx`, `validateBatch.ts`): `tryParseBatch(text, opts?)`; чекбокс
  «Сохранять комментарии» (по умолчанию вкл); загрузка с `{ preserveComments:true }`,
  вставка — со снятием комментариев при снятой галочке. Протокол сообщений и
  `panel.ts`/`insertResult.ts` не менялись (комментарии уже внутри `batchText`).

### ОБЪЕДИНЕНИЕ

Комментарии извлекаются и для пакетов-ОБЪЕДИНЕНИЙ: текст документа режется на участников
по разделителям `ОБЪЕДИНИТЬ [ВСЕ]` верхнего уровня, и комментарии каждого участника
(виды 1–4) привязываются к его QueryModel — то есть к **номеру участника** в объединении.
Состояние webview хранит участников по позициям (`savedQueries`), поэтому удаление/
переименование участника удаляет его комментарии теми же механизмами, что и для пакета.

### Запрос, начинающийся с комментария (открытие из текста)

1С открывает конструктором запрос, текст которого НАЧИНАЕТСЯ со строки-комментария
(`// …` перед `ВЫБРАТЬ`) — и где хвостовой `//` стоит почти на каждой строке. Наш
экстрактор литерала запроса (`queryAtCursor.findQueryAt`) распознаёт запрос по первому
ключевому слову (`startsWithQueryKeyword`), но снимал только ведущие пробелы — ведущий
комментарий «прятал» `ВЫБРАТЬ`, и литерал не опознавался («Не найден текст запроса» →
конструктор не открывался). Исправлено: `stripLeadingTrivia` снимает ведущие пробелы И
строки-комментарии `//…` перед проверкой ключевого слова. Извлечённый текст по-прежнему
сохраняет ведущий комментарий (он уходит в парсер/связыватель). Хвостовые комментарии на
строках ключевых слов (`ВЫБРАТЬ //…`, `ИЗ //…`, `ПОМЕСТИТЬ Вал //…`) не относятся к 4
видам и отбрасываются (как и предписывает спек).

### Тесты

`sdblLexer.comments`, `commentBinder`, `commentsGenerate`, `commentsRoundTrip` (приёмка:
канонический пример пересобирается байт-в-байт; без опции — без комментариев;
идемпотентность; **ОБЪЕДИНЕНИЕ** — комментарии каждого участника байт-в-байт и привязка к
своему номеру), `queryStore.comments` (правила сброса), `queryAtCursor` (распознавание
запроса с ведущим комментарием). Полный прогон `test:unit` — 1304/1304;
`oracleGolden`/`corpusRegression` — без изменений.

## Подфаза 2. Семантическая валидация текста запроса (MCP 1c-md) — 🔬 исследование (2026-06-23)

Спек: [`2026-06-23-phase8.2-validation-research-design.md`](superpowers/specs/2026-06-23-phase8.2-validation-research-design.md) ·
полный отчёт: [`phase8.2-validation-research.md`](phase8.2-validation-research.md).

**Что не так.** Критерий открытия конструктора — чисто синтаксический (`tryParseBatch` →
`parseBatch` не бросил). Парсер не знает метаданных, поэтому запрос на **несуществующую
таблицу открывается**. Эталон из требований не должен открываться, но открывается:

```
ВЫБРАТЬ Валюты.Ссылка КАК Ссылка, Валюты.Наименование КАК Наименование
ИЗ Справочник.Валюты1 КАК Валюты
  ЛЕВОЕ СОЕДИНЕНИЕ Справочник.БанковскиеСчета КАК БанковскиеСчета
  ПО Валюты.ОсновнаяВалюта = БанковскиеСчета.Ссылка
```

(`Справочник.Валюты1` не существует — есть `Справочник.Валюты`).

**Исследование.** Прежде чем менять критерий, охарактеризовали инструмент MCP
`1c-md.validate_query` на **178 проверках** (6 параллельных субагентов, живая база
`smallb`): таблицы, поля/навигация, синтаксис, виртуальные таблицы регистров, сложные
конструкции, реальный корпус `tmp/query1c/` с разметкой `{…}`.

**Итог.** `validate_query` — это **полноценный парсер 1С + сверка с метаданными** (а не
только синтаксис, вопреки описанию). Эталонный «плохой» текст корректно **не открывается**
(`{(5,2)}: Таблица не найдена "Справочник.Валюты1"` + маркер `<<?>>`), исправленный —
открывается.

- ✅ **Проверяет:** существование таблиц/полей/ТЧ, навигацию через точку (только по
  ссылочным), соответствие префикса типа, арность ОБЪЕДИНЕНИЯ, согласованность
  группировки, значения `ЗНАЧЕНИЕ(Перечисление.…)`, применимость виртуальной таблицы к
  типу регистра и состав её параметров, поля ВТ (суффиксы Остаток/Оборот), колонки
  *существующей* ВТ между пакетами, дубль псевдонима. Всегда отдаёт позицию
  `{(строка,столбец)}`.
- ⚠️ **Не проверяет:** существование ВТ по «голому» имени без точки (CTE-семантика), тип
  значений `&П` и параметров ВТ, логику отбора по ресурсу среза.
- ⚠️ **Не поддерживает** скалярный подзапрос `(ВЫБРАТЬ …)` в списке полей.
- ℹ️ Регистронезависим; принимает английский синтаксис и префиксы `Catalog.`/`Document.`;
  при успехе нормализует текст. **Конфигураторную разметку `{…}` принимает как есть** —
  вырезать НЕ нужно, достаточно снять ведущие `|`.

**Рекомендация (отдельной подфазой реализации).** MCP `1c-md` — **только инструмент
исследования, в рантайме расширения не используется ни в коем случае** (никакого вызова
`validate_query` при открытии/«ОК» — расширение не должно зависеть от внешнего сервиса).
Семантическую проверку (существование таблиц/полей) делать **локально по кэшу метаданных**
(Фаза 7.2), который у конструктора уже есть. Исследование лишь показало эталон поведения,
которое нужно воспроизвести локально: какие тексты «открываются», какие — нет, и какие
именно сообщения об ошибке давать. Реализация — за рамками исследования.
