# Фаза 7. Открытие конструктором существующего текста запроса

← [Дорожная карта](ROADMAP.md)

✅ Готово (2026-06-17). Опирается на [Фазу 6](PHASE_6.md) (обратный разбор `parseBatch` →
`QueryModel`).

Фаза 6 научила проект восстанавливать визуальную модель из текста запроса и побайтно
сверять её с оракулом. Фаза 7 — это UX поверх готового парсера: довести до конца сам
жест пользователя «открыть существующий запрос в конструкторе», чтобы он работал из
одной интуитивной команды без лишних кнопок.

## Подфаза 1. Единая команда «1С: Конструктор запроса» — ✅ закрыто

> Задача, возможно, уже поднималась в прошлых фазах (см. `1c.queryConstructorFromCursor`
> и `queryAtCursor.ts` из 6.6), но как рабочая фича до пользователя не доведена.

**Итог.** `1c.queryConstructorFromCursor` удалена (`package.json` + `extension.ts`);
её парсящее поведение стало поведением основной `1c.queryConstructor`. Развилка
«найден / не найден» вынесена в чистый планировщик
[`src/extension/queryConstructorPlan.ts`](../src/extension/queryConstructorPlan.ts)
(`planQueryConstructor` → `findQueryAt`), покрыта юнит-тестами
`test/unit/queryConstructorPlan.test.ts`. Спек и план:
[спек](superpowers/specs/2026-06-17-phase7-single-command-design.md) ·
[план](superpowers/plans/2026-06-17-phase7-single-command.md). `test:unit` 1201/1201.

**Что не так сейчас.** В меню две команды:

- `1c.queryConstructor` — «1С: Конструктор запроса» — открывает конструктор, но **не**
  разбирает запрос под курсором (только запоминает позицию редактора для вставки).
- `1c.queryConstructorFromCursor` — «1С: Конструктор запроса (из позиции)» — содержит
  логику разбора литерала под курсором (`findQueryAt` → `parseBatch` → `loadModel`).

Отдельная кнопка «(из позиции)» не нужна и по факту не работает — её поведение должно
быть поведением **основной** команды.

**Что должно быть.** Остаётся одна команда `1С: Конструктор запроса`. При ПКМ в тексте
запроса (`.bsl`) она:

1. ищет строковый литерал-запрос, в чьих границах лежит курсор (`findQueryAt`);
2. **если найден** — молча разбирает его (`parseBatch`) и открывает конструктор уже
   заполненным (Таблицы, Поля, Условия и т.д.), как если бы запрос собрали руками; при
   сохранении текст возвращается на то же место литерала;
3. **если не найден** — модальный вопрос **«Не найден текст запроса. Создать новый
   запрос?»**; только при согласии открывается пустой конструктор.

Команду `1c.queryConstructorFromCursor` и её пункт меню удаляем (`package.json`,
`src/extension/extension.ts`); парсящую логику переносим в `1c.queryConstructor`.

### Приёмочный сценарий — `tmp/1.bsl`

```bsl
"ВЫБРАТЬ
|	Валюты.Ссылка КАК Ссылка,
|	Валюты.Наименование КАК Наименование
|ИЗ
|	Справочник.Валюты КАК Валюты
|ГДЕ
|	Валюты.Код = &Код"
```

- ПКМ на строках **1–7** (внутри литерала запроса) → конструктор молча открывает
  написанный запрос: заполнены Таблицы (`Справочник.Валюты`), Поля (`Ссылка`,
  `Наименование`), Условия (`Валюты.Код = &Код`).
- ПКМ на строке **8** (вне литерала) → вопрос «Не найден текст запроса. Создать новый
  запрос?».

## Подфаза 2. Ускорение загрузки метаданных — ✅ закрыто

**Что не так было.** Открытие конструктора грузило метаданные через
`loadMetadataFromYaml`, который **на каждое открытие** парсил ~4505 отдельных
YAML-файлов (25 MB) библиотекой `yaml`. Замер на реальной выгрузке (6899 таблиц):
**~13–16 с**. И дерево метаданных, и текст запроса (`loadModel` шлётся после
`await metadataReady`) ждали эти секунды — отсюда оба симптома пользователя.

**Решение.** Консолидированный единый JSON-кэш модели `model-cache.json` рядом с
каталогом `cf/`. Строим полную `MetadataModel` один раз, дальше читаем+парсим **один**
файл. Инвалидация по mtime (скан YAML-дерева ~70 мс) + версии формата
(`MODEL_CACHE_VERSION`). Самовосстановление: первое открытие после парсинга платит
один раз, дальше быстро; повторный парсинг/«Обновить кэш» автоинвалидируют кэш.

Замер «до/после» (`tmp/parser_data/cf`, 6899 таблиц):

```
cold (сборка кэша из YAML):  13481 ms
warm (чтение model-cache):     299 ms   ← ~45x
```

Реализация — pure-TS [`src/core/metadata/modelCache.ts`](../src/core/metadata/modelCache.ts)
(`loadMetadataCached`), подключён в `panel.ts` (с таймингом в OutputChannel),
юнит-тесты `test/unit/modelCache.test.ts` (build-on-miss / cache-hit /
инвалидация по mtime / по версии). Спек+план:
[спек](superpowers/specs/2026-06-17-phase7.2-metadata-cache-design.md) ·
[план](superpowers/plans/2026-06-17-phase7.2-metadata-cache.md). `test:unit` 1205/1205.

## Подфаза 3. Разведка реального конструктора через Playwright — ✅ закрыто

Tooling-драйвер [`tooling/real-constructor/`](../tooling/real-constructor) управляет
**живым** веб-клиентом 1С (УНФ, публикация `host.docker.internal/smallb`) и собирает
визуальный референс настоящего «Конструктора запроса». Это доказывает выполнимость
автоматической сверки (оракул 7.4) и даёт вход для доработки нашего webview.

**Поток (всё probe-verified на реальном клиенте):**

1. `session.ts` — headless Chromium 1600×1000, автологин Администратора; опрос
   `body.innerText` до маркера рабочего стола (long-poll веб-клиента вешает
   `networkidle`); `dismissStartupDialog` гасит блокирующие стартовые модалки.
2. `console.ts` — открытие обработки «Консоль запросов» штатным диалогом
   **«Сервис и настройки» → «Перейти по ссылке…»** (`e1cib/app/Обработка.КонсольЗапросов`):
   смена URL-хэша уже загруженный SPA не перезагружает.
3. `constructor.ts` — текст вставляется в крупнейший `<textarea>` (`insertText`),
   **«Конструктор запроса…» вызывается из контекстного меню поля (ПКМ)**; вкладки
   обходятся по `[data-content]` (подписи рисуются CSS-ом, `textContent` пуст), набор
   читается из DOM (динамический — «Связи» только при >1 таблице); `closeConstructor`
   жмёт «Отмена» между запросами.

**Запуск:** `npm run real:setup` (Chromium), `npm run real:smoke` (эталон
`ЗаказПокупателя` — приёмка выполнимости, 8 вкладок), `npm run real:inventory`
(10 сложных запросов → скриншоты + опись). Скриншоты-референс и опись UI пишутся в
`tmp/phase7.3-real-constructor/<slug>/` (gitignored, не коммитятся) — регенерируются
прогоном `real:inventory`.

**Инфраструктура (этой же подфазы):** read-only bind-mount платформы 1С + `rac` в
контейнере для снятия зомби-сессий через RAS (держат единственную лицензию —
[`docs/ras-sessions.md`](ras-sessions.md)); установка Microsoft Core Fonts в
`post-create.sh` (без них веб-клиент показывает блокирующий диалог о шрифтах).

Pure-логика (конфиг, страж рекурсии, имена скриншотов, логгер) — под vitest
(`test:unit` 1219/1219); браузерный драйвер — приёмкой `real:smoke`. Спек+план:
[спек](superpowers/specs/2026-06-17-phase7.3-real-constructor-recon-design.md) ·
[план](superpowers/plans/2026-06-17-phase7.3-real-constructor-recon.md).

## Подфаза 4. Опись UI нашего конструктора — ✅ закрыто

Симметрично описи реального конструктора (7.3) снят визуальный референс **нашего**
webview-«Конструктора запроса» на тех же 10 сложных запросах корпуса. Tooling-драйвер
[`tooling/our-constructor/`](../tooling/our-constructor) поднимает собранный бандл webview
(`out/webview/main.js`) в headless Chromium, наполняет его реальными метаданными
(`tmp/parser_data/model-cache.json`, 6899 таблиц), на каждый запрос шлёт `loadModel` (текст
разбирается обратным парсером Фазы 6, `parseBatch`) и обходит **видимые** вкладки (набор
динамический — вычисляется в `App.tsx`), по скриншоту на вкладку. Живой 1С **не нужен** —
конструктор полностью локальный (тот же приём, что `test/e2e`).

**Запуск:** `npm run our:inventory` — собирает webview, копирует бандл и метаданные в harness,
поднимает `serve`, прогоняет драйвер. Скриншоты-референс и опись UI пишутся в
`tmp/phase7.4-our-constructor/<slug>/` (gitignored, не коммитятся — регенерируются прогоном),
полная опись — `tmp/phase7.4-our-constructor/INVENTORY.md`. Единственное изменение
production-кода — атрибут `data-tab` на вкладках `TabsBar` (тестовый хук обхода).

Результат — все 10 запросов загрузились без ошибок парсинга; набор вкладок на скриншотах
соответствует динамической логике (`«Связи»` при > 1 таблице, `«Индекс»` при типе «Создание ВТ»).

**Сопоставление «наш конструктор vs реальный»** (вход в доработку):

| Аспект | Реальный | Наш |
|---|---|---|
| Совпадают | Таблицы и поля · Группировка · Условия · Дополнительно · Индекс(ы) · Объединения/Псевдонимы · Итоги · Пакет запросов; динамика «Связи»/«Индекс» | то же |
| Лишние вкладки | — | **«Порядок»**, **«Построитель»** (нашего происхождения) |

| Нижняя панель | дропдауны «Редактируемый запрос/оператор» + Запрос/ОК/Отмена/? | одна «Запрос»; «Вставить»/«Отмена» в «Таблицы и поля»; контекст пакета — правый вертикальный стрип |
| Тип запроса | 3 радио | 4 (добавлен «Уничтожение ВТ») |
| «Обновить кэш» | — | есть (ускорение метаданных, Подфаза 2) |

## Подфаза 6. Корпусная проверка UI по фиче-векторам — ✅ закрыто

Pure-TS ядро [`tooling/corpus-verify/`](../tooling/corpus-verify): разбирает каждый из
**17 933** запросов корпуса обратным парсером Фазы 6 (`parseBatch`), извлекает фиче-вектор
(`features.ts`: пакет/объединение/число таблиц/виды соединений/тип запроса/индексы/
группировка/итоги/порядок/условия/подзапросы/виртуальные таблицы/параметры/построитель/
ТЧ/выражения/первые-N/различные), группирует в **классы эквивалентности** (`classes.ts`)
и берёт представителей самых крупных классов. Драйвер (`verify.ts`, Playwright + harness
7.4) на каждый запрос поднимает **свежий** webview (как боевой `createPanel`), шлёт
`loadModel`, **обходит все видимые вкладки** и проверяет чистые **инварианты**
(`invariants.ts`): структурные (`checkStructure` — набор/порядок вкладок == ожидаемому по
фиче-вектору, число таблиц в панели == модели) один раз на «Таблицы и поля»; контентные
(`checkContent` — нет дублей полей, нет обрезки текста без тултипа) на КАЖДОЙ вкладке, с
аккумуляцией и дедупликацией нарушений; плюс отсутствие `pageerror`. Скриншот — только на
нарушение; отчёт покрытия — `report.ts`.

Pure-логика под vitest (`test:unit` 1238/1238: фиче-вектор, классы/выборка, инварианты,
отчёт). Прогон: `npm run corpus:verify` (опц. `PER_CLASS`, `MAX_SAMPLE`). Результат —
3119 классов, 92 запроса не разобрались (граница парсера, вход в будущую фазу); прогон
**200 представителей** крупнейших классов (~66 % корпуса по объёму) — **0 нарушений**:
вкладки (включая переименование «Индексы») и отрисовка таблиц корректны на всём
многообразии форм. Артефакты (`REPORT.md`, скриншоты) — регенерируемые в
`tmp/phase7.6-corpus-verify/` (gitignored).

**Триаж-находка (зафиксирована):** один долгоживущий webview после ~3 `loadModel`
переставал отрисовывать панель «Таблицы» (накопление состояния). На пользователя **не
влияет** — `createPanel` всегда создаёт новый webview и шлёт `loadModel` один раз; драйвер
повторяет это перезагрузкой на запрос. Драйвер **обходит все вкладки**, поэтому контентные
инварианты `DUP_FIELDS`/`CLIP` реально задействованы (проверено: на «Порядок» запроса
ЗаказПокупателя — 31 поле без дублей, т.е. фикс E2 подтверждён корпусно; `CLIP` сканирует
`span` всех вкладок). Хук `data-field-source` стоит на **всех** списках-источниках: «Порядок»,
«Группировка», «Итоги», «Индекс» (строятся из `selectedFields` — к ним применён
`distinctFieldRefs`, тот же фикс E2) и «Условия» (дерево метаданных — по-табличные группы,
чтобы одно имя поля в разных таблицах не давало ложный дубль). Проверено: на ЗаказПокупателя
Группировка/Итоги/Порядок = 31 поле без дублей, Условия = по-табличные группы (160/3); прогон
40 представителей с обходом вкладок — 0 нарушений (`DUP_FIELDS` больше не инертен ни на одной
вкладке).

## Подфаза 8. Доработки UI: открытие, источники, видимость вкладок — ✅ закрыто

Девять независимых доработок поверх готового конструктора:

- **7.8.1 Тёплый кэш после «Обновить кэш».** `parseConfiguration` переписывал YAML и
  инвалидировал `model-cache.json` → первое открытие сессии платило холодный разбор
  (~13 с). Добавлен `rebuildModelCache` (`modelCache.ts`, общий `writeModelCache`),
  вызывается в `panel.ts` сразу после обновления — следующее открытие тёплое.
- **7.8.2 Открывать сразу заполненным.** Хост шлёт `init { hasInitialQuery }` перед
  `metadataTree`; вебвью держит оверлей загрузки до готовности (метаданные, а при
  входном тексте — до `loadModel`) — пустой конструктор больше не мигает.
- **7.8.3 Отдельное окно.** Настройка `queryConsole.openInNewWindow` (default true);
  после `createPanel` — `workbench.action.moveEditorToNewWindow` (VS Code 1.85+, ошибка
  на неподдерживающих платформах гасится).
- **7.8.4 «+» в «Поля».** Работала только при фокусе таблицы; теперь доступна при ≥1
  таблице, открывает «Произвольное выражение» (поля всех таблиц) → новое поле. e2e.
- **7.8.5 Двойной клик по полю** открывает «Произвольное выражение» (предзаполнено) и
  правит поле на месте (`SET_FIELD_EXPRESSION`). e2e.
- **7.8.6 Перетаскивание таблицы в «Поля»** добавляет ВСЕ её поля
  (`ADD_ALL_FIELDS_WITH_TABLE`); строки списка «Таблицы» сделаны draggable. e2e.
- **7.8.7 Видимость вкладок** — классический сегментный вид `TabsBar` (разделители,
  утопленные неактивные, верхний акцент у активной).

### 7.8.8-fix. Открытие из текста источника-подзапроса не показывало его поля

Дефект (см. `tmp/1с/Снимок экрана_20260619_091306.png`): при открытии конструктором
текста с источником `ИЗ … , (ВЫБРАТЬ …) КАК ВложенныйЗапрос` конструктор не видел полей
вложенного запроса. Корень: парсер (`sdblParser.parseTableSource`) отдаёт такой источник
с пустым `fullName` и без колонок (колонки живут только в `subquery.members[].model.fields`),
а UI (`fieldsForTable`/`TablesPanel`) резолвит колонки по `fullName` через синтетическую
метатаблицу `ТабличнаяЧасть`. Интерактивная ветка `ADD_SUBQUERY_TABLE` такую метатаблицу
создаёт — открытие из текста (`LOAD_BATCH`) нет.

Фикс — единая точка в редьюсере `LOAD_BATCH` (`queryStore.ts`): новый
`synthesizeSubqueryTables` обходит весь пакет (запросы → участники объединения → таблицы)
и каждому источнику-подзапросу с пустым `fullName` назначает уникальное имя (по `alias`,
default `ВложенныйЗапрос`) и собирает синтетическую `ТабличнаяЧасть` с колонками из
`deriveUnionColumns`. Псевдоним `alias` не трогаем — генератор печатает `КАК <alias>`
(`defaultTableAlias` отдаёт `alias` первым), поэтому round-trip текста не меняется. Массив
`tables` пересоздаётся только при наличии подзапросов (иначе ссылка сохраняется). Так как
вложенный конструктор (`NestedConstructorModal`) грузит подзапрос тем же `LOAD_BATCH`,
рекурсивная вложенность чинится автоматически на каждом уровне. Тесты —
`queryStore.loadBatch.test.ts` (+3: синтез колонок, сохранение ссылки `tables`, round-trip).
`tsc` чист, `test:unit` 1270/1270, `test:e2e` 16/16.

### 7.8.8-fix2. Коллизия id таблиц после открытия из текста (подзапрос + ВТ)

Дефект (см. `tmp/1с/Снимок экрана_20260619_093122.png` / `…_093255.png`): после открытия
запроса с источником-подзапросом и добавления временной таблицы конструктор путал ВТ и
подзапрос — при раскрытии полей раскрывались обе таблицы сразу, а сохранённый текст
становился `(ВЫБРАТЬ …) КАК ВТ, ВТ КАК ВТ1` с полями `ВТ1.…`. Корень (воспроизведено
скриптом): парсер нумерует таблицы **позиционно** (`t0`, `t1`, … в каждом запросе), а
интерактивные добавления (`ADD_TABLE`/`ADD_TEMP_TABLE`/`ADD_SUBQUERY_TABLE`/произвольные
поля) берут id из общего `_tableCounter` (старт 0). После `LOAD_BATCH` счётчик не
синхронизировался → первая добавленная таблица получала `t1`, уже занятый загруженной
таблицей. `resolveAliases` ключует псевдонимы по id (поздняя таблица затирала псевдоним
ранней), а `TablesPanel` ключует по id и состояние раскрытия, и React-`key` — отсюда оба
симптома из одного корня. Баг общий (любой загруженный запрос ≥2 таблиц + добавление), его
проявила фича подзапроса/ВТ.

Фикс — `syncTableCounter(doc)` в начале `LOAD_BATCH`: обходит все запросы пакета →
участники объединения → таблицы, берёт максимальный числовой суффикс id (`/^t(\d+)$/`) и
поднимает `_tableCounter` до него (монотонно, через `Math.max`). Следующая добавленная
таблица получает свободный id. Вложенный конструктор (`NestedConstructorModal`) делит тот
же модульный счётчик и тоже зовёт `syncTableCounter` в своём `LOAD_BATCH` — безопасно
(монотонность; id нужны уникальными лишь внутри одного `selectedTables`). Тест —
`queryStore.tableIdCollision.test.ts` (отдельный файл: `_tableCounter` — модульное
состояние, в общем файле прогретый счётчик скрыл бы баг). `tsc` чист, `test:unit`
1271/1271, `test:e2e` 16/16.

### 7.8.8-fix3. Ссылка на временную таблицу при открытии из текста

Дефект: при открытии текста с источником-ссылкой на внешнюю ВТ (`ИЗ ВТ КАК ВТ`, без
`ПОМЕСТИТЬ` в самом запросе) двойной клик по ВТ не открывал окно временной таблицы, а
раскрытие не показывало её полей. Корень: парсер отдаёт такую ссылку обычным
`SelectedTable` `{fullName:"ВТ", alias:"ВТ"}` — без флага `tempTable` и без синтетической
метатаблицы. UI ветвит двойной клик по `subquery`→`tempTable`→«все поля» и резолвит
колонки по синтетической `ТабличнаяЧасть` (по `fullName`) — для ВТ ни того, ни другого
не было. Существующий `inferUndefinedTempTables` (фаза 6.19) синтезирует колонки ВТ только
при ссылке `*`/`Алиас.*`; конкретная ссылка `ВТ.asdfa` его не включает, и результат живёт
в резолвере парсера, а не в `state.tables` конструктора.

Фикс — `synthesizeTempTables` в `LOAD_BATCH` (после `synthesizeSubqueryTables`,
`queryStore.ts`): источник считается ссылкой на ВТ, если он не подзапрос, не виртуальная

псевдониму (`ВТ.asdfa`), поэтому prefix-исключение НЕ применяется. Такому источнику
ставится `tempTable:true` (ДО `docToSnapshot`) и собирается синтетическая `ТабличнаяЧасть`
с колонками из
`collectTempColumns` — различимые первые сегменты путей, на которые ссылаются поля ВТ в
выборке/условиях/группировке/порядке/итогах (объединение по всем участникам пакета: одно
имя ВТ = одна метатаблица). Генерация не меняется (источник печатается `ВТ КАК ВТ`; флаг
`tempTable` генератор не читает). Изменение целиком на стороне webview — парсер/генератор и
golden/oracle-корпус не тронуты. Тесты — `queryStore.loadBatch.test.ts` (+4: пометка ВТ и
синтез колонок, реальные таблицы не помечаются, round-trip, `&`-источник ВТ `&ВТ КАК ВТ`
помечается и синтезирует колонки). `tsc` чист, `test:unit` 1275/1275, `test:e2e` 16/16.

### 7.8.19. Хвостовой зарезервированный идентификатор в поле выборки — синтаксическая ошибка

Дефект: `ВЫБРАТЬ Банки.Ссылка Ссылка ИЗ Справочник.Банки КАК Банки` молча принимался и
давал мусор (`Банки.Ссылка Банки.Ссылка КАК Поле1`). Реальный 1С (`validate_query`)
запрос отвергает. Корень: `Ссылка` в верхнем регистре = `ССЫЛКА` — зарезервированное слово
(`EXPR_STOP_WORDS`), поэтому логика неявного псевдонима (`parseOneField`) корректно НЕ
снимает его как псевдоним, но тело `[Банки, ., Ссылка, Ссылка]` проваливалось в обработку
выражения и переквалифицировалось. Проверка 7.8.18 (два ident-подряд, ни один не стоп-слово)

### 7.8.20. Полоса участников ОБЪЕДИНЕНИЯ запроса пакета

Дефект: при открытии пакета, где запрос — ОБЪЕДИНЕНИЕ (`ВЫБРАТЬ … ОБЪЕДИНИТЬ ВСЕ
ВЫБРАТЬ …`), боковая полоса показывала только запросы пакета (`Пакет1`, `Запрос пакета 2`),
но НЕ участников объединения активного запроса (`Запрос 1`, `Запрос 2`). Данные были в
состоянии (`queryList`/`activeQuery`), переключение работало только на вкладке
«Объединения/Псевдонимы». Эталон 1С (`tmp/1с/Снимок экрана_20260619_131859.png`) показывает
участников вложенной полосой рядом с полосой пакета.

Фикс — вторая вертикальная полоса `union-strip` в `ConstructorView`: участники
`state.queryList` активного запроса (если их > 1 и активна не вкладка «Пакет запросов»),
переключение `SET_ACTIVE_QUERY` (та же логика, что у `UnionsTab`). Полоса участников —
внутренняя (левее), полоса пакета — внешняя (правее), как в 1С. Работает и для одиночного
ОБЪЕДИНЕНИЯ-запроса (без пакета). Только UI, состояние/редьюсеры не менялись.

Тест — e2e (+1): на `Пакет1` (2 участника) видны обе полосы и `Запрос 1`/`Запрос 2`; на
`Запрос пакета 2` (1 участник) полоса участников исчезает; назад — снова видна. `tsc` чист,
`test:unit` 1282/1282, `test:e2e` 22/22.
