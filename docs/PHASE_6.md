## ✅ 6.10. Форматер произвольных выражений (`ВЫБОР`, многострочные условия)

Самый крупный остаток. У конструктора 1С есть собственный «красивый вывод» для любых
выражений в `ГДЕ`, в условиях соединения и в полях выборки: он переносит длинные
`И`/`ИЛИ` на новые строки с отступом по глубине, оборачивает отдельные слагаемые в
скобки (`a` \n `И (b)`), раскладывает оператор `ВЫБОР … КОГДА … ТОГДА … ИНАЧЕ … КОНЕЦ`
(CASE), убирает/ставит пробелы по своим правилам. Мы же сейчас храним такие выражения
как сырой текст и отдаём почти как есть — отсюда расхождения.

Это рычаг по большей части из 437 расхождений: запросов с `ВЫБОР` и многострочными
условиями в `ГДЕ`/`ИМЕЮЩИЕ`/соединениях. Метаданные не нужны.

Реализован самодостаточный модуль `src/core/query/exprFormatter.ts`: переотрисовывает
**только структуру** (булево дерево `ИЛИ`/`И`/`НЕ`, оператор `ВЫБОР`, скобки OR-групп),
а текст листьев (сравнения, вызовы функций, `МЕЖДУ a И b`, `ЕСТЬ НЕ NULL`, …) сохраняет
дословным срезом исходника — это даёт нулевой риск регрессий листового текста. Лексер
и парсер не тронуты (форматер сам ре-токенизирует выражение и распознаёт `ИЛИ`/`НЕ`/
`ВЫБОР`/… по верхнему регистру). Подключён в `sdblGenerator`: `ГДЕ`/`ИМЕЮЩИЕ` (base 1),
поля выборки (value-слот), составные условия соединений `ПО` (base 2, по-конъюнктное
оборачивание). `needsFormatting` срабатывает только при наличии OR- или CASE-узла —
ранее принятые простые выражения остаются байт-в-байт.

Правила отступов (вычитаны по оракулу, проверены побайтно): OR — `ИЛИ` на base+2 (1-й
уровень) / +1 (глубже), группа в скобках; `ВЫБОР` — `КОГДА=E+1, ТОГДА=E+2, ИНАЧЕ=E+1,
КОНЕЦ=E`, где `E` = контентный отступ слота (+1 для boolean-слота).

**Итог 6.10:** принято **1392 → 1417**, mismatch 437 → 412, parse-exception 147
(без изменений), 0 регрессий принятых. Весь оставшийся остаток (412 mismatch + 147
parse-exception) учтён по классам в **6.12** (подзапросы вынесены в 6.11).

## ✅ 6.11. Подзапрос в источнике «ИЗ» (вложенный запрос как узел модели)

1С разрешает писать в `ИЗ` не таблицу, а вложенный запрос: `ИЗ (ВЫБРАТЬ … ) КАК Данные`,
в том числе с `ОБЪЕДИНИТЬ` внутри. Модель источника была только таблицей, поэтому такие
запросы не парсились: в корпусе их **65, отклонялись все**.

Сделано: `SelectedTable` получил необязательное поле `subquery?: QueryDocument` —
источник-подзапрос стал полноценным узлом модели. `parseTableSource` поглощает
сбалансированную скобку, рекурсивно разбирает содержимое через `parseDocument`
(поддержка вложенного `ОБЪЕДИНИТЬ`), требует обязательный `КАК <алиас>`. `renderSource`
рендерит подзапрос реверсивно: `generateDocument` подзапроса реиндентируется на +1 таб,
`(` на первой строке, `) КАК <алиас>` на последней (пустая строка-разделитель
`ОБЪЕДИНИТЬ` → строка из одного таба, как у конструктора). Изменения гейтятся наличием
`subquery`/`(` — для запросов без подзапросов разбор и вывод байт-в-байт прежние.

**Итог 6.11:** все 65 подзапросов-источников теперь парсятся (0 parse-exception по этому
классу). Принято **1417 → 1444** (+27), parse-exception 147 → 94 (−53), mismatch 412 → 438
(+26 — подзапросы, которые парсятся, но чей вложенный текст ещё расходится по форматеру:
`ВЫБОР`/`В (ВЫБРАТЬ …)` внутри, отступ подзапроса-участника соединения → 6.12-C). **0
регрессий** ранее принятых.

Подзапрос после оператора `В (ВЫБРАТЬ …)` (94 случая) **вынесен в 6.12-C**: его отступ
контекстно-зависим (зависит от позиции `В` в произвольном выражении), завязан на форматер
6.10 и не сводится к чистому правилу; остаётся `custom`-выражением.

## ✅ 6.12. Зачистка остатка приёмки (метаданно-независимые классы закрыты; остаток задокументирован)

**Цель — ноль.** Оракул `validate_query(input).query_text` детерминирован: это
канонический текст объекта `СхемаЗапроса` конструктора, один и тот же для одного input.
Раз конструктор принял текст (`valid: true`) и выдал `query_text`, значит у него **есть
модель** этого запроса — а значит её можно воспроизвести. Поэтому цель проекта — принять
**все 1976 валидных** (`report.json` пуст: mismatch = 0, parse-exception = 0). 112
oracle-invalid конструктор отвергает сам — у них нет эталона, они вне знаменателя.

**Итог 6.12 (коммиты `6.12.1`–`6.12.27`):** принято **1417 → 1717** (87% валидных),
**parse-exception 147 → 0**, mismatch **412 → 259**. Последняя серия `6.12.11`–`6.12.27`
(последовательные субагенты, по одному классу; гейт 6.7 + `npm run test:unit`, ноль

**Закрыто серией `6.12.11`–`6.12.27`** (каждый — oracle-фикс + курируемая фикстура
`test/fixtures/oracle/`):
- Скобки `(НЕ <поле>)` в ГДЕ при дословном хвосте; хвостовой пробел квирка `ЕСТЬ НЕ NULL`.

- **Сохранение порядка источников соединения** (seed не переупорядочивается по операнду
  условия — `renderFrom` берёт текстовый seed, а не таблицу из ПО).
- Разбор `Таблица.ТЧ.(поля)` (голые и квалифицированные имена) в ВЫБРАТЬ; `&Параметр` в
  `ИНДЕКСИРОВАТЬ ПО`/`УПОРЯДОЧИТЬ ПО`; **бесисточниковый ПОМЕСТИТЬ** (был пустой вывод).
- **Удаление ведущих нулей** в числах (`ДАТАВРЕМЯ(2000, 01, 01)`→`(2000, 1, 1)`) — широко
  нагруженное, **+28**. Литерал периода (`ДЕНЬ/МЕСЯЦ/…`) в верхнем регистре как аргумент
  даты-функции.
- `МЕЖДУ a И b` инлайн (внутренний `И` не принимается за конъюнкт); список `В (a, b)`
  сплющивается в одну строку.
- **`ГДЕ` останавливается на `ИТОГИ`/`ИНДЕКСИРОВАТЬ`/`ДЛЯ`/`УПОРЯДОЧИТЬ`/`ИМЕЮЩИЕ`**
  (`WHERE_STOP` был неполон → секции засасывались в последнее условие и выводились
  дословно с грязным отступом) — нагруженное, **+40**; плюс квалификация полей секций.

**Неустранимый остаток (259), задокументирован по критерию фазы:**
1. **Скобки условий — внутренний флаг конструктора (~86).** `ПО (a=b)` ¦ `ПО a=b`,
   `И (cond)` ¦ `И cond`, ведущая скобка OR-группы, `В (&X)` ¦ `В(&X)`. Зависит от того,
   построено ли условие реляционным редактором (→ скобки) или введено как произвольное
   выражение (→ без скобок) — **внутренняя классификация `СхемаЗапроса`, не восстановимая
   из канонического текста и не выводимая из схемы метаданных**. Гипотеза «оборачивать по
   разрешимости операндов» построена и **строго опровергнута**: 228 wrap / 111 bare при
   resolved|resolved, контрпример — самосоединение одного регистра (первое соединение bare,
   прочие wrap); все варианты предиката давали чистую регрессию приёмки.
2. **Квалификация полей по метаданным — ограничена покрытием схемы (~54).** `Поле` ¦
   `Таблица.Поле`, `* КАК Поле1`, имена источников для temp/`&Параметр`/подзапросных
   таблиц. Резолвер метаданных построен (`MetadataResolver`, опциональная инъекция в
   `parseBatch`, чистый путь байт-в-байт), но применимое множество на корпусе **пусто**:
   бара́е поля ссылаются на источники вне YAML-схемы (ВТ `ПОМЕСТИТЬ`, `&Параметр`,
   подзапросные псевдонимы) — резолвер корректно возвращает «неизвестно». `УПОРЯДОЧИТЬ ПО`
   тоже не чистое правило (114 принятых держат поле бара́м; принудительно — −7). Резолвер
   не закоммичен (приёмка не растёт; чистый путь сохранён).
3. **Контекстно-зависимый отступ + оракул-side преобразования.** Отступ подзапроса в
   value-слоте (`(ВЫБРАТЬ ПЕРВЫЕ 1`) и `КОГДА` во вложенном `ВЫБОР` расходятся **в обе
   стороны** (+1/−1 таб) по глубине контекста — не одно правило. Плюс оракул-side: пустой
   вывод для `ВЫБРАТЬ * ИЗ &Параметр`, переписывание агрегатов — делается конструктором из
   метаданных, которых у нас нет.

Дальнейший прогресс по классу 1 требует харвеста *внутреннего* представления соединения
конструктора (флаг «простое условие» vs «произвольное») — отдельная итерация сбора данных,
а не текстовое/схемное правило.

**B. Квалификация полей по метаданным (R3-семейство, метаданно-зависимое):**
- Бара́е поле выборки/порядка/итогов разрешается конструктором в `Таблица.Поле` по схеме
  (`Ссылка КАК Поле1` → `Пользователи.Ссылка КАК Ссылка`; `УПОРЯДОЧИТЬ ПО Поле` →
  `Таблица.Поле`). В остатке: `УПОРЯДОЧИТЬ` **≈47** + множество «`Поле1`-полей» выборки.
- Разблокируется проводкой **необязательного резолвера метаданных** в `parseBatch` (и в
  headless-оракул — грузит ту же YAML-схему из `src/cf`, что вебвью отдаёт через
  `SET_METADATA`). Парсер по умолчанию остаётся чистым (text→model).

**C. Доводка форматера/генератора (метаданно-независимое, точечно по оракулу):**
- `ВЫБОР`-остаток **≈50** и `ИЛИ`-остаток **≈30** — структура не сошлась в краевых случаях
  6.10.
- Скобки `ПО`: одиночное условие то оборачивается `ПО (a = b)`, то нет `ПО a = b` —
  правило R5 неполно (**десятки кейсов** `ПО (…)` ¦ `ПО …`).
- Скобки `НЕ`-конъюнкта: контекстно то `И НЕ x`, то `И (НЕ x)` (**≈9+**).
- `В (&a, &b)` — у **списка** значений конструктор сохраняет пробел `В (`, в отличие от
  одиночного `В(&Список)` из R4 (**≈11**).
- Нормализация пробелов оператора в **модельных** условиях: `a =b` → `a = b` (лист
  дословный сейчас сохраняет тесную форму).
- Хвостовой `;`/разделитель пакета (**≈7**), хвостовой пробел листа (`ЕСТЬ НЕ NULL `),
  `ВЫРАЗИТЬ` (**≈10**), `ИТОГИ` (**≈12**), `МЕЖДУ` (**≈6**).
- Пропуск модификатора `РАЗРЕШЕННЫЕ` (`ВЫБРАТЬ РАЗЛИЧНЫЕ` ¦ `ВЫБРАТЬ РАЗРЕШЕННЫЕ
  РАЗЛИЧНЫЕ`) — парсер не выставляет `selection.allowed` в части случаев.

**D. Верность структуры пакетов/объединений:**
- Кейсы, где расходится весь запрос (другой источник, `ВЫБРАТЬ` ¦ строка из 80 `/`) —
  разный разбор границ пакета/объединения; перепроверить `parseBatch`/`parseDocument` на
  этих файлах.

**E. Толерантность к форматированию разработчика.** Разработчик пишет текст произвольно —
не так, как выводит конструктор; наш разбор обязан нормализовать так же:
- **Регистр ключевых слов.** `ВЫБРАТЬ` ≡ `Выбрать` ≡ `ВыбРАть`; регистр идентификаторов при
  этом **сохраняется**.
- **Пробелы и переносы.** Любое число пробелов/табов/переводов строк эквивалентно;
  однострочный и многострочный разбираются одинаково.

```
конструктор:                вариант 1 разработчика:        вариант 2 разработчика:
ВЫБРАТЬ                      Выбрать Поля.Поле              ВыбРАть       Поля.Поле
	Поля.Поле КАК Поле          из &Параметр КАК Поля          иЗ          &Параметр
ИЗ                                                             КАК  Поля
```

Базовая толерантность уже есть (лексер приводит ключевые слова к верхнему регистру,

## ✅ 6.13. Стандартные vs произвольные условия связи (скобки `ПО` + галочка «Произвольное»)

Класс скобок `ПО`, ошибочно помеченный в 6.12 неустранимым, **закрыт** по правилу,
подтверждённому конструктором 1С (скриншоты): при соединении двух таблиц **стандартное**
условие связи (`ЛевойТаблицы.Поле <оп> ПравойТаблицы.Поле`, задаётся мышкой в редакторе
связи) печатается **без скобок**; **произвольное** (параметр/константа/функция в операнде,

## ✅ 6.14. ГДЕ/ИМЕЮЩИЕ как список условий (И-сплющивание, скобки по ИЛИ)

Правило пользователя (проверено живым оракулом MCP `validate_query`, скриншоты
`tmp/screenshots/…07-*.png`): `ГДЕ` — **список условий через `И`**; условия делятся на
стандартные/произвольные (галочка «Произвольное»), но скобки зависят не от этого —
**блок в скобках ⟺ внутри блока есть `ИЛИ`**:

- **И-сплющивание**: скобочная группа без внутреннего верхнеуровневого `ИЛИ` сплющивается
  в список (рекурсивно; `(a И (b ИЛИ c))` → `a` + `(b ИЛИ c)`).
- **Голый верхнеуровневый `ИЛИ`** сливает весь `ГДЕ` в **один** произвольный блок в скобках
  (`И` связывает сильнее `ИЛИ`; раньше парсер семантически неверно резал по `И`).
- **ИМЕЮЩИЕ**: те же правила, разделитель — **завершающее ` И`** (у `ГДЕ` — ведущее).
- **НЕ-блок**: `НЕ(` слитно, скобки всегда сохраняются, продолжения на ind+orDelta+1.

Фикстура `0061` (6.12.11) оказалась неверной (живой MCP: `(НЕ predicate)` снимает скобки
в ГДЕ), исправлена; `13-where.sdbl` реканонизирован; +14 MCP-проверенных фикстур
`0091`–`0104`. Вкладка «Условия» открывает запрос с корректными галочками «Произвольное»
(биндинг `c.custom` существовал с 5.2, классификация парсера исправлена).

**6.14.4 — стандартное условие только с параметром справа.** Мышкой в редакторе условия
литерал не задать ⇒ стандартным остаётся лишь `Поле <оп> &Параметр` (`= &П`, `В(&П)` /
`В ИЕРАРХИИ(&П)`, `МЕЖДУ &а И &б`, `ПОДОБНО &Ш`; допускается `&П.Поле`). Литерал,
`ЗНАЧЕНИЕ(…)`, список, поле или подзапрос справа → «Произвольное» (галочка П.). Текст
запроса не меняется ни на байт: expression custom-условия строится общим
